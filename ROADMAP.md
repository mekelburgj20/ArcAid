## Open Followups

- **`score:new:global` bumps every category card of a game (surfaced by ADR 0016 P4, v2.59.0)** — the live-score socket event carries no engine, so the optimistic client-side bump increments `score_count` on *all* of a game's cards rather than the one the score belongs to. Harmless before P4 (one card per game, so it was correct); now visibly wrong when a game has a Simulation and an Arcade-Style board. Fix is to widen the event payload with the score's engine (and let the client resolve the category with `engineCardCategory`) — deliberately out of P4's scope because it touches the websocket contract. Self-heals on the next fetch; only the optimistic interval is wrong.
- **No way out of the room admin area (user request 2026-07-31)** — once inside `/:slug/admin/*` there is no navigation back to the public game room or to the landing page; the only escapes are editing the URL or opening a new tab. Two fixes, both small: (1) a "back to room" affordance in `RoomAdminLayout` pointing at `/:slug`, and (2) **make the Arcaid wordmark a link to `/` everywhere it renders** — it already is on some surfaces (`GlobalScoreboard`, `LandingPage`) and is inert in the admin layouts, which is the inconsistency. `BrandWordmark` is the shared component and the natural place to make the link the default rather than something each caller remembers to add. Check `SuperAdminLayout` too — same trap.
- **Personal-best lookup in game rooms (user request 2026-07-31)** — the Global Scoreboard's *My Score* density mode makes finding your PB easy there, but the room-scoped "Room Scores" surface has no equivalent, and a player with scores across many games has no quick way to answer "what's my best on X?". Suggested shape (user's): put it on the player's Stats page as a **searchable Personal Bests list, filterable by game name**. Data already exists — `StatsService.getPersonalBests` is the obvious source (note the known doctrine violation logged against it: it still reads `submissions` rather than `score_history`, which should be corrected in the same pass). Consider also reusing the A5a `My Score` density idea on room cards, but the searchable list is the smaller, higher-value first step.
- **Catalogue still describes legacy platforms, not engines + device availability (ADR 0016 gap, found 2026-07-31)** — ADR 0016 states the catalogue should hold an **engine** list, with device compatibility expressed separately. No phase implemented it: importers still write legacy ids into `global_games.platforms` (`VPS_FORMAT_MAP` emits `pinball_fx`, `bam`, …), and none reference `scoreProvenance`. Two live consequences: **(a)** the AtGames importer tags games with `atgames`, which is a *device*, so an AtGames-only game offers no derivable engine and its submissions auto-lock to `unknown` — this is one of the two ongoing sources of unknown-engine scores; **(b)** `bam` is still carried as if it were a platform when ADR 0016 demoted it to a catalogue tag on the `fp` engine. Fix is a phase, not a tweak: map every importer's source format to engines, express AtGames/VR/standalone as **device availability**, and migrate existing `global_games.platforms`. Until then `enginesFromLegacyPlatforms` translates at read time and the categories themselves stay correct (they derive from *score* engine, not the catalogue). **✅ SHIPPED in v2.62.0:** migration 129 folded the catalogue to engines+features via the shared `foldCataloguePlatforms` (all seven importers route through it), AtGames games carry `atgames_native`, device-required rules match explicit availability, prod-rehearsed. Residue for a future sweep: 3 pre-existing empty-platform placeholder rows (incl. a stray `[Pending Pick]` catalogue row from the pin path), and `standalone_other` device rules match nothing (catalogue doesn't record it). Remove this entry on next ROADMAP sweep.
- **Global Scoreboard sort-toggle row overflows at 320px (found during v2.61.0 screenshot loop, 2026-08-01)** — the `flex flex-wrap` sort control row (`Popular / Recent activity / Top rated / Most scores / A–Z`) produces ~74px of horizontal page overflow on 320px viewports. Pre-existing, unrelated to the title lockup (which fits). Fix direction: allow the row to wrap fully or make it horizontally scrollable within its own container.
- **iScored-synced scores can never record provenance (ADR 0016 gap, found 2026-07-31)** — `ScoreSyncPoller` reads `tournaments.iscored_default_engine` / `iscored_default_device` to stamp synced rows, but **there is no admin UI to set either column** (zero references in `admin-ui/` or `schemas.ts`), so both are always NULL and every synced score lands `unknown`/`unknown`. Verified on prod: **all 6 `source='sync'` rows are `unknown`**, and 5 of 37 games with global scores already show a real card beside an Unspecified one. **RESOLVED IN DESIGN — AND THE ANSWER IS TO BUILD NOTHING HERE.** The product owner's decision (2026-07-31) is recorded in ADR 0016 under *"iScored-synced scores never reach the Global Scoreboard"*: sync stays tournament-only, synced scores are **always `unknown`** (no inference, no admin UI, no per-tournament default — `iscored_default_engine`/`_device` become vestigial and unread), and they are **excluded from `global_scores`**. Rationale: iScored is a stopgap during migration, so inference machinery would invest in a path the product intends to retire; a player who wants a score on the global board enters it in Arcaid. The unknown-engine problem this entry described is therefore not fixed but **made irrelevant** for synced rows. Folded into **P2** — see `tmp/engine-device-p2-contract.md`. **✅ SHIPPED in v2.60.0:** both import paths stamp `unknown`/`unknown` unconditionally, `fanOutFromRoomSubmission` rejects `source:'sync'` at the service, and migration 128 purged the sync-origin + unknown-engine residue. Remove this entry on next ROADMAP sweep.
- **Proof photos are too buried on room scoreboard cards (user request 2026-07-29, deferred by the user until the UX redesign arc completes)** — a score row on a room scoreboard card gives no obvious route to the proof photo attached to it; today you have to know to open the game detail page and expand the player's history. Desired behavior: **clicking the score itself opens the proof photo directly**, the way iScored does it. Scope when picked up: the score cell becomes the affordance (not a separate icon) wherever a proof photo exists — `ScoreList`/`BannerCard`/`ShowcaseCard`/`MinimalCard` on the room scoreboard first, then the game-detail history rows — with a no-op (and no hover affordance) when the row has no photo. Photos already live under `/api/score-photos`; this is presentation only, no schema or upload change. Build nothing until the redesign arc lands — the row layout it would hang off is still moving.
- **Submission-draft commit bypasses the username lock (v2.54.0 deferral)** — `POST /submission-drafts/:stateParam/commit` (`global.ts`) commits under `draft.playerName`, a free-text name typed *while a guest* that gets attributed to the just-authenticated user after the claim-prompt OAuth handoff. Every direct authed submit path now resolves the name server-side (`UserProfileService.resolveSubmitName`), but this handoff path still honors the typed name. Left deliberately: the draft name also drives the self-claim merge sweep, so resolving it canonically changes which anon identities get self-claimed — needs a design decision (resolve-and-still-sweep-by-typed-name is the likely shape), not just a code swap.
- **Guest multi-name collapse on the community leaderboard (v2.54.0 deferral)** — `CommunityScoreService.getGameLeaderboard` now collapses a logged-in player's aliases into one rank via the three-leg identity key, but guests partition on the `iscored:<typed name>` fallback, so one guest submitting under several names still holds several ranks. Their identity is genuinely unknown, so there is nothing to collapse on — admin merge remains the remedy.
- **Kiosk mode on approval rooms — not supported (approval-rooms contract, v2.39.0)** — `KioskScoreboard.tsx` has no login flow, so an 'approval'-policy room's kiosk display can only ever show the graceful "requires approval" message (it never resolves member/admin viewer_status). A future `KIOSK_KEY` pairing mechanism — a per-room secret the kiosk device stores once and sends on every request, verified server-side as an admin-equivalent view grant scoped to that one room — would let a physically-secured kiosk display an approval room without exposing it to the wider internet. Not built this release; do not build ad-hoc bypasses (e.g. a query-param backdoor) in the meantime.
- **Guild-implies-membership for Discord cross-room read commands (approval-rooms contract, v2.39.0)** — `discordExcludedRoomIds()` (`src/utils/discordRoomFilter.ts`) excludes ALL 'approval'-policy rooms from `/list-active`, `/list-scores`, `/list-winners`, `/view-selection`, `/view-stats` — even for a Discord user who is actually a guild member (and thus arguably entitled to see the room via that guild's own membership implication). Today there's no per-command viewer-identity check against `RoomAccessService.canViewRoom`, just a blanket room-level exclusion — simplest safe default, but stricter than necessary. Refinement: thread the invoking Discord user's ID + the target room's guild through to a per-command membership check instead of a global exclusion list.
- **Google avatars don't show on leaderboards/rankings yet (Google login contract, 2026-07-24)** — `PlayerAvatar` (`admin-ui/src/components/ScoreboardComponents.tsx`) now accepts an `avatarUrl` prop and prefers it via `resolveAvatarUrl()`, and `GET /api/global/recent-scores` + `FriendsService.getFriends` ship `avatar_url` end-to-end (landing-page ticker + Friends page show Google avatars correctly). The other 6 BE queries documented in CLAUDE.md's "Display-name resolution in BE leaderboard queries" section (`LeaderboardService.recalculate`, `GlobalLeaderboardService.recalculate` ×2, `RankingService.calculateOverallRankings`, `StatsService.getOverallStats`/`getAllPlayerStats`/`getRoomOverview`) still only SELECT `up.avatar_hash` from their existing `user_profiles` join — add `up.avatar_url` to each SELECT + response shape (no new joins needed), then thread an `avatarUrl`/`avatar_url` field through the ~8 `<PlayerAvatar>` call sites' TS interfaces (`GameLeaderboard`, `RankedEntry`, etc.) and JSX props. Until then, a Google-identified player's avatar falls back to the initials placeholder on every leaderboard/ranking/stats surface — degrades gracefully, no broken images, just a cosmetic gap. Mechanical follow-up, ~half day.
- **Encrypt `DISCORD_CLIENT_SECRET` at rest (Google login contract, 2026-07-24)** — `GOOGLE_CLIENT_SECRET` was added to `ENCRYPTED_SETTING_KEYS` when Google OAuth shipped; `DISCORD_CLIENT_SECRET` was deliberately left OUT of the allowlist in the same change, because the existing prod value is stored plaintext and adding it to the allowlist would make `decryptSecret` throw on read the next time settings are loaded (`isEncrypted()` fails the `enc:v1:` prefix check on the current plaintext row). To close this gap: either (a) re-save the value via the Global Settings UI once the key is in the allowlist (triggers encrypt-on-write, but requires a maintenance window where Discord OAuth briefly can't decrypt until the re-save lands), or (b) write a one-time migration that reads the current plaintext value and re-writes it through `encryptSecret()`. Do (b) before flipping the allowlist to avoid the window in (a).

### Content moderation: report a room / name + blocklist + admin action tools (S22 core, user-asked 2026-07-25)

1. **Prevention at input (blocklist) — SHIPPED v2.43.0 (S22 Phase 1).** Curated, normalized (case/l33t/diacritic/zero-width-folded) blocklist check on room name, slug, tournament names, and display names/room-name claims at create/rename/claim time. Unambiguous-slurs-only to avoid the Scunthorpe problem. Catches low-effort abuse; never catches determined creativity (that's what reports are for).
2. **Report → admin queue (the backbone) — SHIPPED v2.43.0 (S22 Phase 1).** Report affordances on rooms and player names → a unified super-admin Reports page (`content_reports` table, `ContentReportService`) with type tabs (Rooms / Player Names / Scores) — the Scores tab also gives the pre-existing, previously-consumerless `score_reports` admin API its first UI. Reuses the v2.39.0 join-request admin-queue UI pattern (list + dismiss/resolve actions + nav badge).
3. **Admin action tools (make reports meaningful) — SHIPPED v2.44.0 (S22 Phase 2), partially.** Super-admin: **suspend room** (hidden + inaccessible pending review, including to the room's own admins — softer than delete; six enforcement seams covered, see CHANGELOG), **admin display-name reset** (clear-to-null only — free-text rename deferred), **ban identity at token issuance** (Discord/Google OAuth callbacks, refresh, room creation — ties to `IdentityLinkService.resolveCanonical` + the two-directions-of-a-link check). Room rename/delete still route through the existing Game Rooms manager (unchanged from Phase 1). **Not shipped**: room-tier (per-room) bans, ban content cascade/hiding, per-submit/comment ban enforcement, ban Discord DM — see the fuller "C. Admin ban" workflow below, now partially superseded by what shipped here.
4. **(Optional, later) automated screening.** Async cheap-LLM (Haiku-class) pass on new room names/descriptions that FLAGS to the queue rather than blocking. v2 nicety, not launch-critical.

Accountability foundation already shipped: room creation requires login, is capped (3/user), rate-limited, and kill-switchable (v2.33.0) — identity friction is the strongest deterrent.

### Score comments + comment voting/flagging (idea captured 2026-07-11)

Comment on a specific person's score from the room score surfaces, with optional Discord cross-post, upvotes, and a report/flag → mod-review loop. Natural companion to S22 moderation (which already owes the comment-moderation FE wiring S11 deferred) or Phase C social. Rough sizing: ~2–2.5 days total.

**A. Per-score comments (anchor, don't fragment)**

- **Do NOT add a third comment store.** `game_comments` + `global_game_comments` are already flagged as fragmented (see "Comments & Tips — bidirectional view" below). Instead add an optional **score anchor** to `game_comments`: a `score_history_id` column plus denormalized context (`iscored_username`, `score`) so a score comment is just a game comment pointing at a score row.
- **Anchor durability:** scores are deletable (per-row delete, admin wipe, S12 account-delete anonymize). The denormalized context lets a comment survive its score's deletion and render "on a removed score" instead of dangling — ADR 0005 unlink-don't-cascade philosophy. Bonus: S12's account-deletion purge already covers `game_comments`, so the privacy floor needs no reopening.
- **Who can comment: Discord-authed only** (this is the ROADMAP's planned direction for comments anyway — §B below; cross-post needs a real identity; and commenting on a *person's score* is a harassment vector in a way game tips aren't). Guests read-only + "log in to comment" CTA. Reuse the S11 delete-authz tiers (author / room_admin-in-room / super_admin), rate limiters, and auto-audit verbatim.
- **Routing nuance:** "is this a tournament score" is a property of the score EVENT (`score_history.submitted_during_tournament_id`), not the game — the new Room Scores tab shows all-time rows with no tournament of their own. Route by the score's tournament.
- **UX home:** the per-player history expand rows in `GameDetail.tsx` (already exist — lowest-friction surface) + the card quick-view. Historical view = the existing comment list, filterable to a score/player.

**B. Discord cross-post (opt-in per comment)**

- **The channel cascade already exists:** `resolveAnnouncementChannelId(gameRoomId, tournamentChannelId)` in `src/utils/discord.ts` — tournament `discord_channel_id` → per-room `DISCORD_ANNOUNCEMENT_CHANNEL_ID` → env fallback → `null`. The feature calls it; on `null` show "No linked Discord channel — ask your room admin to set one."
- **Explicit opt-in checkbox per comment, default OFF** — posting to Discord publishes to the whole guild; never by surprise.
- Gate on the room's `DISCORD_ENABLED` + bot-in-guild (S10 `getDiscordClient()` health accessor) + a per-room admin toggle (e.g. `SCORE_COMMENT_DISCORD_ENABLED`) so admins can kill the firehose without disabling comments.
- Embed: commenter display name/avatar, the comment, score + game context, deep link to `/:slug/games/:name`.
- Optional adjacency: "someone commented on your score" DM to the score owner — a sixth `NotificationService` type, default-off, managed via `/arcaid-notifications`.

**C. Upvotes on tips/comments + Top sort**

- New `comment_votes (comment_id, voter_discord_id, created_at, UNIQUE(comment_id, voter_discord_id))` — one vote per Discord user, toggle to un-vote. **Discord-authed only** — deliberately NOT keyed on the spoofable `x-user-id` (that keying is exactly the ballot-stuffing weakness already logged against `RatingService` in Open Followups).
- Applies to BOTH score-anchored comments and existing game tips (same table — another payoff of not fragmenting stores).
- Sort control on comment lists: **Top** (vote count desc, tie-break newest) | **Newest**. Default Top for game tips (surfaces the best pro tip), Newest for a score's thread. Vote counts ship in the list response (single LEFT JOIN + GROUP BY, no N+1); FE shows count + the viewer's own-vote state.

**D. Report/flag → mod review**

- New `comment_reports` mirroring the existing `score_reports` shape exactly (`id, comment_id, reporter_discord_id, reason, created_at, resolved_at, resolved_by, resolution`) + UNIQUE(comment_id, reporter_discord_id) so one user can't spam-report one comment. Reporting = Discord-authed; one tap + optional reason.
- **Mod queue** on the room admin side (natural sibling of the planned "report a problem" game-info queue — consider one shared "Reports" admin page with type tabs): list open reports with comment + context, actions = **dismiss** (resolve, comment stays) / **remove** (delete via the existing S11-tier delete path, auto-audited). Super-admin sees cross-room.
- Optional threshold: auto-HIDE (not delete) a comment at N open reports pending review — ship OFF by default; manual review is the floor.
- Report volume is admin-visible; consider folding an "open reports" count into the S10 admin health card later.

**Open questions to settle at build time:** (1) do existing anon-authored tips get grandfathered read-only (recommended — matches §B below)? (2) does the Top sort need time-decay (recommend no — keep it simple, tips are evergreen)? (3) auto-hide threshold value if enabled (suggest 3).

### Player Self-Service + Moderation

Three related features that together tighten up score/comment integrity and give admins a proper moderation surface. All gated behind Discord-authenticated identity — anonymous users don't get self-service edit/delete (they have no durable identity to verify), don't get to leave comments/tips, and don't need to be "banned" because the claim system auto-suffixes them anyway.

**A. Self-edit / self-delete scores**

Logged-in players can correct or remove their own submissions across every surface where their score appears.

- [ ] **Delete own score** — button/icon on each score row where `submitted_by_user_id === viewer's Discord ID`. Applies to `submissions`, `community_scores`, `score_history`, AND the fanned-out `global_scores` row for the same event. Soft-delete (set `deleted_at` / `orphaned_at`) rather than hard-delete so audit trail survives.
- [ ] **Edit own score value** — modal with new score input + photo upload. Gated on ownership. Writes a new `score_history` row for the revision, updates the canonical `submissions` / `community_scores` row to the new value, re-fans to `global_scores` (delete old global row + insert new). Photo required if the game's room requires photos on new submits.
- [ ] **Scope consistency** — deleting/editing a room score automatically mirrors to the global row (via `submitted_from_room_id` + `submitted_during_tournament_id` linkage). Deleting a pure global submission only affects `global_scores`.
- [ ] **Self-actions logged to `audit_log`** with actor, target row id, old/new values. Room admin + super-admin can see via the activity log.
- [ ] **Rate limit** — e.g., 10 self-edits per user per hour to prevent leaderboard thrashing.
- [ ] **UX** — edit/delete controls on: Tournament card rows (expanded view), Game Detail leaderboard rows, Community tab rows, Global Scoreboard rows, Global Game Detail rows. Hidden for non-owners.

Open design question: **should edit be allowed to raise a score or only lower it?** Raising is abusable without photo-proof verification. Safe default: edits require a new photo if photos are required for submission in that room; otherwise any value is allowed but all edits are logged.

**B. Comments/tips require Discord login**

Currently `POST /:roomId/comments/:gameName` and the global `/global/games/:id/comments` both accept anonymous posts. Change the gate.

- [ ] **Server** — add `requireDiscordUser` middleware to comment POST endpoints (room + global). Reject 401 without a valid player token. Existing anon comments stay visible but read-only.
- [ ] **Client** — comment compose UI hides or replaces with "Log in to leave a tip" CTA when viewer isn't Discord-authenticated. Same for rating.
- [ ] **Self-edit / self-delete comments** — same ownership rule as scores. Logged-in users see edit + delete controls on their own comments on Room Game Detail and Global Game Detail. Soft-delete (set `deleted_at`), audit-logged.
- [ ] **Legacy anon comments** — kept as-is, visible but no owner controls. Admin can still delete them from the mod surface.

**C. Admin ban — logged-in users**

`user_bans` table already exists (used by `GlobalScoreService.isBanned` to short-circuit global submissions). Build out the full moderation workflow around it.

- [x] **Admin ban UI — SHIPPED v2.44.0 (S22 Phase 2).** Reports page "Bans" tab (super-admin, global) — not a standalone `/admin/bans` route as originally sketched, but same functionality: list current bans (active/expired/lifted), add a ban (provider id + reason + optional duration), lift a ban. No room-admin-scoped variant (bans are global-only, per the shipped scope below). `POST /admin/bans` also gained the `iscored:*` synthetic-id rejection Phase 1 only added to the score-report ban route.
- [x] **Ban scope** — SHIPPED v2.44.0: global-only (a ban blocks login/room-creation everywhere). **SHIPPED v2.49.0: room-tier bans** — nullable `user_bans.game_room_id` (migrations 122/123, same table, not a separate one). A room ban only blocks that ONE room (submit/comment/join/join-request) and strips the banned user's `room_members` row on ban (lifting does not auto-restore membership — they can re-join); it never blocks global surfaces (Global Scoreboard, friends), other rooms, or reporting the room itself to super-admins (`POST /global/rooms/:roomId/report` deliberately uses a global-only ban gate — a room admin cannot ban a user to suppress escalation of their own room). A global ban still blocks everywhere, rooms included. Room admins manage room bans from `/:slug/members` (Ban button per member + a "Banned" section, admin-viewer-only), gated the same way as the existing per-row score-delete admin detection on public pages (decoded `playerToken` claims — `role === room_admin`/`super_admin` — falling back to the admin-token slot for admins who logged in directly at `/:slug/admin`). Guards: can't self-ban, can't ban a super admin, can't ban a room admin of that room (403 — that's a super-admin matter), evaluated across the full identity-link candidate set (`BanService.expandIdentityCandidates`) so a grant held on a linked `google:*` alias can't be routed around; ban insert + membership strip + pending-join-request denial are one transaction with a pre-flight duplicate-active-ban check (409). The roster a room admin sees already excludes actively-banned users server-side. Super-admin Reports "Bans" tab is additive: a scope column (Global vs. room name) now renders across every ban row; the standalone add-ban form there stays global-only. **Still NOT shipped:** existing content orphaning on ban (see "Ban → content cascade" below — unaffected by the room-tier ban), and a DM-based Discord notification of the ban.
- [x] **Enforcement points** — SHIPPED v2.44.0: token issuance (Discord/Google OAuth callback, refresh) + room creation, via `BanService.isIdentityBanned` (checks both directions of an `IdentityLinkService` link). **SHIPPED v2.47.0 (S22 follow-ups):** per-submit/write enforcement at every identified chokepoint — room submissions (community/tournament/freeplay scores), comment POSTs, friend POSTs, join-request/self-join, catalogue proposals, profile display-name changes, room-admin content writes (announcements, lobby config, settings, tournaments, styles upload), Discord `/submit-score` and `/pick-game` — via the shared `requireNotBanned` middleware (Express routes) plus inline `BanService.isIdentityBanned` checks (Discord commands, which have no Express chain). Rating POSTs are explicitly OUT of scope (`rooms.ts` ratings endpoint is `x-user-id`-only, no JWT — nothing to ban-gate). **Known limitation, not closed by this release:** enforcement is identity-based — on guest-allowed paths (comments always accept anon; score submits in `REQUIRE_DISCORD_LOGIN=false` rooms; ratings) a banned user can trivially write anonymously by omitting their token. Closing the anon-tier gap (device fingerprinting, IP-based limits, or similar) is a separate, harder problem, not attempted here.

### Phantom anon-claim cleanup — manual runbook (not automation)

First-claim-wins is the policy: whoever uses a name first in a room owns it. **We don't automate "Discord trumps anon" name transfers** — that's the fraud surface we explicitly rejected when the design was agreed. If a Discord user and a legit-different-human anon share a display name, the anon (who got there first) keeps it, the Discord user gets `Name_2`.

The one exception is a phantom claim — an anon row that *is actually the same human* as the Discord user who later tries to claim the name, typically from the pre-v2.2.5 window when `conditionalRequireDiscordUser` was dropping Bearer tokens in guest-allowed rooms. Those should be cleaned up case-by-case, never automated.

**Procedure:**

1. Verify the claim is a phantom. Needs at least two of:
   - The anon claim's `claimed_at` falls inside a known middleware-bug window (pre-v2.2.5 deploy, or after any future auth-middleware regression).
   - The user confirms it was their browser session.
   - The `anon_token` matches a localStorage UUID the user can produce.
2. Identify the row precisely:
   ```sql
   SELECT anon_token, room_id, display_name, claimed_at
     FROM anon_room_claims
    WHERE LOWER(display_name) = LOWER('<name>')
      AND room_id = '<room-uuid>';
   ```
3. Delete narrow, keyed on `anon_token` + `room_id` + `display_name`:
   ```sql
   DELETE FROM anon_room_claims
    WHERE anon_token = '<token>'
      AND room_id = '<room-uuid>'
      AND LOWER(display_name) = LOWER('<name>');
   ```
4. Log the deletion in `audit_log` with a reason so there's a trail (or document in ops notes if the table doesn't accept ad-hoc reasons).

**Do not:**
- Run the broad `DELETE ... WHERE name IN (SELECT iscored_username FROM user_mappings)` form. It can't distinguish phantom from legit and violates first-claim-wins.
- Surface a self-serve "claim this name" button in the UI — same fraud surface.
- Build a background job that auto-cleans phantoms. Needs a human to verify the claim is actually the same user.

The existing admin merge tool at `/:slug/admin/identity` is the right place for real cross-identity reconciliation when it turns out two claims should collapse into one.

### iScored Sync Hardening

Cooldown enforcement gaps identified in v2.2.0 review. Evaluate and address in a future sprint.

- [ ] **Cooldown bypass via `/sync-state`** — when an admin manually creates a game on iScored tagged `DG` / `WG-VPXS` / `WG-VR` / `MG`, the next `/sync-state` creates a local `games` row set to ACTIVE with no `GAME_ELIGIBILITY_DAYS` / `last_played` check (`src/discord/commands/syncstate.ts:45-65`). The game goes live in ArcAid even if `game_library` says it's still in cooldown. Cooldown is only enforced by `runMaintenance()`, `autoPickAndActivate()`, and the web `/pick-game` path — not by sync. Decide: (a) treat sync as admin-override and document, (b) refuse to create the local row when cooldown applies, or (c) create it as LOCKED so it's recorded but doesn't surface on scoreboards. Option (c) preserves iScored-is-source-of-truth while respecting cooldown.
- [ ] **Duplicate active games when sync runs with an active DG game present** — related to above. Sync doesn't check `max_active_games` before marking a discovered game ACTIVE, so two DG games can be ACTIVE simultaneously until the next maintenance run rotates one out.

#### High Availability Notes

Current constraints: SQLite (single-writer), singleton engine classes (in-memory state), Playwright persistent sessions (local disk).

| Approach | Effort | Notes |
|----------|--------|-------|
| Active-passive failover | Low | 2 containers, 1 active. Docker restart policy + health checks. Shared volume for SQLite. |
| Read replicas (Litestream) | Medium | SQLite WAL mode + Litestream replication. One writer, N readers. Public scoreboard benefits most. |
| Separate concerns | Medium | Stateless API container (scales horizontally) + singleton engine/scheduler container. Requires DB change. |
| Migrate to PostgreSQL | High | True multi-container with connection pooling. Rewrite all raw SQL + migrations. Biggest payoff, largest effort. |

**Quick wins:** Docker `restart: always` + health check, Litestream for continuous S3 backups, reverse proxy (nginx/Caddy) for SSL/rate limiting, CDN for static assets. **Recommendation:** Start with active-passive + Litestream, migrate to PostgreSQL when scale demands it.
