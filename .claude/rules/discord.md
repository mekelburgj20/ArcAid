# Discord bot, slash commands, announcements, notifications — rules

Loads when you touch the Discord client/commands, Discord utils, chat responses (callouts), notifications, lobby feed or friends. Cross-cutting invariants live in the root CLAUDE.md; this file is the detail for this domain.

## OAuth and credentials
- **Discord OAuth state encoding.** `__super__` → super-admin login, `player:<slug>` → public-page player login, bare slug → room admin login. Scope must be `identify` only — `guilds.members.read` causes 400s on the authorize redirect.
- **Per-room Discord/iScored credentials** live in `game_room_settings`: `DISCORD_GUILD_ID`, `DISCORD_ANNOUNCE_CHANNEL_ID`, `ISCORED_USERNAME`, `ISCORED_PASSWORD`, `ISCORED_GAMEROOM`, plus `DISCORD_ENABLED` / `ISCORED_ENABLED` toggles. The bot token + Discord client ID/secret stay global.

## Guild-scoped slash commands
- **Slash commands are guild-scoped (v2.120.1).** Reads (`/list-active`, `/list-scores`, `/list-winners`, `/view-queue`, `/view-stats`) and the tournament-id admin commands (`/run-cleanup`, `/nominate-picker`, `/pause-pick`) resolve `resolveGuildReadScope(interaction.guildId)` in `src/utils/discordRoomFilter.ts` — rooms whose `DISCORD_GUILD_ID` is the invoking server, minus Discord-off/suspended rooms, and minus approval rooms the invoking Discord user is not a member or admin of. Legacy env-guild fallback covers settingless rooms; no link or DM → ephemeral not-linked reply, nothing shown.
  - Signatures: `resolveGuildReadScope(guildId, userId)` / `validateDiscordWriteTarget(roomId, guildId, userId)` (v2.212.0). `GuildReadScope.notMemberOf` lets a command say "join the room" instead of "nothing to show". An omitted userId excludes, so every new caller must pass `interaction.user.id`.
- **`/join` (v2.222.0, E12) resolves rooms WITHOUT the membership filter** (the one command that must see approval rooms it is not a member of: `DISCORD_GUILD_ID` + legacy env fallback, minus Discord-off rooms) and joins through `JoinRequestService` / `RoomMembershipService.addMember`, never a direct `room_members` insert.
- **Writes resolve their room via `discordWriteTarget.ts`.** **Any new command that reads or mutates room data must go through one of those two** — a bare `FROM tournaments`/`FROM games` in a command is a cross-room leak. Known residue: `StatsService.getGameStats`/`getPlayerStats` and the five tournament/game autocompletes are still cross-room (queued).

## Per-room slash-command policy (v2.217.0, E7)
- **`game_room_settings.DISCORD_COMMAND_POLICY`** (JSON `{version, defaults{channelIds, roleIds, publicRoleIds}, commands{name: {enabled, channelIds, roleIds, publicRoleIds, ephemeral}}}`, edited instant-save in Room Settings -> Discord -> Slash commands, `components/DiscordCommandPolicy.tsx`) turns commands off, locks them to Discord channels/roles, or makes their replies visible to everyone.
- **Inheritance.** Absent/malformed key = everything allowed; an unlisted command is on and uses `defaults`; a command's NON-EMPTY list replaces the default list; empty = any; ANY listed role passes.
- **Two role tiers (v2.224.0, E15).** `roleIds` = may use it, private reply; `publicRoleIds` = may use it, reply visible to everyone (absent = `[]`, inherits like `roleIds`). ALLOWED = effective `roleIds ∪ publicRoleIds` empty or held (refusal names the union); VISIBLE = `ephemeral: false` OR the member holds an effective `publicRoleIds` role. Default roles gate PLAYER commands too: the UI captions the defaults and warns when they gate a player command (`listCommands().adminOnly === false`, i.e. no `default_member_permissions`; E14). A refused autocomplete answers ONE explanatory choice (`policyRefusedAutocompleteChoices`, value `POLICY_REFUSED_CHOICE_VALUE`), never `respond([])`; the chat-input gate refuses the same member before a command sees the sentinel.
- **Read only through `parseCommandPolicy`** (`src/utils/discordCommandPolicy.ts`); the settings POST re-serializes the value through it.
- **`commandPolicyDecision(guildId, userId, commandName, channelId, memberRoleIds)` is the ONE gate** → `{refusal, ephemeral}`; `commandPolicyBlockReason` is its refusal half (autocomplete, tests). `DiscordClient`'s InteractionCreate calls it for chat-input commands (after `guildInteractionBlockReason`, ephemeral refusal) AND autocomplete (one explanatory choice, v2.224.0). A guild linked to several rooms allows a command when ANY non-excluded room allows it; any error ALLOWS (fail-open).
- **Replies are ephemeral by default (v2.218.0, E9; Mox 2026-11-02).** Each command rule carries `ephemeral` (absent = true; `false` = "Visible to everyone" in the UI, the only value that changes anything). When the decision says ephemeral, the dispatcher calls `forceEphemeralReplies(interaction)` BEFORE `command.execute`: it wraps `reply` / `deferReply` / `followUp` on the instance to add `MessageFlags.Ephemeral` (and drops any `ephemeral` key, discord.js 14.17+ deprecation), so no command needs its own ephemeral handling and `editReply` inherits the deferred flag. Visible = the command's own choices stand (its error replies stay ephemeral). `channel.send` announcements are never replies and are untouched. DMs and unlinked guilds are ephemeral. Several rooms on one guild: visible only when EVERY allowing room says so.
- **A new interaction entry point (buttons, modals, context menus) must call the decision too** and apply `forceEphemeralReplies` when it says ephemeral. A command that must post publicly regardless of the switch (none today) would send a `channel.send`, not a reply.
- **A reply is only a substitute for an announcement when it is public.** `/pick-game` and `/activate-game` pass `skipChannelId: interaction.ephemeral ? undefined : interaction.channelId` to `announceGameActivated`; a new command that dedupes a channel post against its own reply must test `interaction.ephemeral` (set by discord.js at defer/reply time) the same way, or a private reply silently swallows the announcement.
- **Refusals and failures are activity rows (G14, ADR 0037):** `DiscordClient` records every policy / room-gate refusal and command failure (`ActivityLogService.recordCommandRefusal`, one `problem` row per room linked to the guild); `sendChannelEmbed`/`sendChannelMessage` record a failed post with Discord's error on the rooms using that channel (`recordBotPostFailure`). Successful commands are NOT logged. A new entry point or send helper records its refusals/failures the same way.
- Arcaid Chat Responses (`callouts.ts`) is deliberately outside it (own channel allowlist). Refusal copy names roles via `listGuildRoles`, never ids.

## Announcements and mentions (v2.155.7)
- **`TournamentEngine.activateGame` announces NOTHING** (it runs inside three callers' transactions). Every INTERACTIVE activation — web `/pick-game`, Discord `/pick-game`, the admin page, `/activate-game` — calls `engine.announceGameActivated(...)` after COMMIT, fire-and-forget. The cron/queue/auto-pick paths keep their own richer embeds. A new interactive activation that skips the call is the silent-web-pick bug reborn (rtx_pinball Daily Grind, 2026-09-07).
- **A `<@id>` that lives only inside an embed neither pings nor renders reliably** (Discord notifies on content mentions only and resolves embed mentions from the viewer's local cache; a fresh login shows a raw snowflake). Anything that ADDRESSES a player uses `resolveUserMention` → `sendChannelEmbed(channelId, embed, { pingUserIds })`; anything that merely RECORDS a player (the Rotation `Winner:` line, "picked by" on the activation embed) uses a bold name. Never re-add a bare `<@id>` to an embed.
- **Every pick prompt names its tournament in the title AND body (v2.157.1)** — Pick Needed, Winner Timed Out, Pick Reminder, the nominee onboarding post and the Picks-page banner; several tournaments announce into one channel (bofgi, Weekly Grind VPXS, 2026-09-30). Locked by `pick-prompts-name-tournament.test.ts`.
- **Discord `/pick-game` placeholder fulfillment (v2.9.0).** The Discord command mirrors the web `/pick-game` route's three-branch flow: pending+full repurposes the placeholder (keeps `queue_order = NULL` so it stays at the front of the queue); open-slot drops any existing placeholder inside the activate transaction; no-pending+full queues normally.
- **Per-kind announcement channels (v2.221.0, E8; v2.226.0, E16).** Four kinds (`ANNOUNCE_KINDS`): `tournament`, `picks`, `polls`, `scores`. ROOM: `game_room_settings.DISCORD_ANNOUNCE_ROUTES` (`{version:1, routes:{kind: id}}`, every route optional, Room Settings -> Discord -> Announcement channels, `components/DiscordAnnounceRoutes.tsx`, instant-save) is read only through `parseAnnounceRoutes` (the settings POST re-serializes through it). TOURNAMENT: `tournaments.discord_announce_routes` (migration 208, same shape, a value may be `'none'`) is read only through `parseTournamentAnnounceRoutes` and written through `serializeTournamentAnnounceRoutes` (schema + `TournamentService`; omitted on update = unchanged); `discord_channel_id` stays the whole-tournament catch-all (`''` / id / `'none'`). Both in `src/utils/discordAnnounceRoutes.ts`; the form side is `lib/announceRoutes.ts` + `components/TournamentAnnounceRoutes.tsx`, channels via `hooks/useGuildChannels.ts`.
  - **Precedence, `resolveAnnouncementChannelId(room, catchAll, kind, tournamentRoutes?)`:** Discord off → null; tournament `routes[kind]` (`none` → null, id → it); catch-all (`none` → null, id → it); room `routes[kind]` (for `scores` with none, the room `tournament` route); room `DISCORD_ANNOUNCEMENT_CHANNEL_ID`; env; null. **Every caller that reads a tournament's `discord_channel_id` must select and pass `discord_announce_routes` too** (TimeoutManager, TournamentEngine, EventScheduler, SeasonPollService, `/pick-game`, DiscordScorePostService); a `SELECT t.*` carries it.
  - Every send names its kind: `tournament` = tells players the tournament's state (Now Active, Rotation, Congrats, season standings, event posts, poll "Next up"); `picks` = addresses a picker or an admin (Pick Needed/Reminder, Winner Timed Out, No X Queued/Selected/Eligible, nominee onboarding); `polls` = about a poll; `scores` = top-N glory/dethrone posts. A new send picks its kind by that rule. The maintenance path resolves `channelId` (tournament) and `picksChannelId` once and threads both.
- **Forum targets get a post per message (v2.221.0, E8).** `sendChannelEmbed` / `sendChannelMessage` / `postPoll` check `getChannelType` (gateway cache, else `GET /channels/:id`, cached per process; unknown = text, the old behaviour) and, for a forum/media channel, `POST Routes.threads(forumId)` with the body as `message` and `name` = embed title / first content line / poll question (`forumPostName`, 100 chars, no raw mentions). `postPoll` returns the thread id as `channelId` and **`season_polls.discord_channel_id` stores the THREAD id**, so voters/expire/edit and every later poll notice (`pollChannelFor`, never the resolver) land in that thread.
  - **A forum poll is TWO messages (v2.235.1, E19):** Discord silently ignores `poll` on a forum starter message, so `postPoll` creates the post with `starterContent` only (`SeasonPollService.buildHeadline`: question + Lobby link, no tally — the tally edits target the poll message) and then `POST Routes.channelMessages(threadId)` with the poll; `discord_message_id` is that POLL message, never the thread id. `fetchAnswerVoters` warns a 404 / 10102 Unknown poll once per message (`ok: false` stays, so no vote is removed).
- **Top-N score posts (v2.225.0, E13).** `DiscordScorePostService.onScoreRanked` is called from `LobbyFeedGenerator.onScoreSubmitted` (the ONE score hook; every source; independent of the feed toggles) and posts plain text, kind `scores` (v2.226.0), when `DISCORD_SCORE_POSTS_ENABLED` is on and rank <= `DISCORD_SCORE_POSTS_TOP_N` (both read only through `src/utils/discordScorePosts.ts`). The switch and Top N are ROOM-wide by owner ruling (2026-11-06); a tournament goes quiet by setting its Top-score posts row to Don't post, never by a per-tournament switch. Names via the label chain, `allowed_mentions: {parse: []}`. In a forum it posts into `games.discord_thread_id` (migration 207): stored by the "Now Active" announcers (`rememberActivationThread` on the `sendChannelEmbed` result), created lazily by the first score post — only when the `scores` channel IS the `tournament` channel; a separate scores forum keeps its per-game thread in memory and never touches the stored one. A new activation announcer that posts "Now Active" should pass its send result there too.
- **Embed colors:** daily=gold(0xFFD700), weekly=blue(0x00BFFF), monthly=purple(0xAA00FF), custom=green(0x00FF88).
- **Discord ActionRow** holds max 5 buttons. Star-rating + Skip required splitting into multiple rows.

## "Arcaid Chat Responses" (internally still `callouts`, v2.123.0 → v2.125.0)
- **Storage.** `callouts` table (migrations 155/156: `category` ∈ `help|callouts|banter|easter_eggs`) edited via Admin → Settings → Arcaid Chat Responses (upload/replace/export JSON, inline editor, category filter); `CalloutService` caches in memory. The `callouts` table is the ONLY source of truth — the legacy `data/callouts.json` seed file was deleted 2026-08-23 (prod's list is newer/larger); `seedFromFileIfEmpty` still no-ops when the file is absent, so a fresh install starts with just the auto-seeded `help` rows. `ensureBuiltinHelpEntries()` seeds one `help` row per live `action` that has no row.
- **Per-room keys.** `CHAT_RESPONSES_ENABLED` (absent = off), `_CATEGORIES` (JSON array, absent → `["help","callouts"]`), `_CHANNEL_IDS` (JSON array, empty = any readable channel), `_COOLDOWN_SEC` (default 30; `help` never throttled). The room card saves these INSTANTLY (changed keys only, rollback on failure) — NOT via the Save bar (a staged-only toggle let the bot keep replying after the owner "turned it off"). Legacy `CALLOUTS_ENABLED`/`CALLOUTS_CHANNEL_ID` are migrated at boot then deleted.
- **One-by-one choices: `CHAT_RESPONSES_SELECTION`** (`{version:1, only:{category: [key]}}`, the checklist under each kind in the room card, instant-save). A category ABSENT from `only` answers with everything in it, later additions included; PRESENT = exactly the listed keys (empty = none), so a response added later stays off until ticked. Read only through `parseChatSelection`; the settings POST re-serializes through `serializeChatSelection`. **A response is identified by `calloutEntryKey` (`action:<action>` or `trigger:<first inclusion trigger, lower-cased>`), never the row id** — `replaceAll` re-inserts the table, so ids change on every upload. `roomAllowsEntry(config, entry)` is the ONE test (category on AND ticked); the room's list comes from `GET /rooms/:roomId/admin/chat-responses` (globally enabled entries only).
- **Gate order in `src/discord/callouts.ts`:** DM → legacy `ENABLE_CALLOUTS='false'` → guild scope → room master → allowed channels → in-chat "Arcaid, shush/unmute" → per-user mute (`notification_prefs.chatResponses`) → filter to the entries some permitting room answers with (`roomAllowsEntry`) BEFORE matching → match → per-channel cooldown → reply.
- **Live `action`s:** `active_games`, `picks_link`, `scores_link`, `how_to_submit`, `time_left` (cron-parser, tournament tz), `leaders`, `my_rank`, `pick_status`, `tournament_rules`, `how_to_claim`. Static responses may use `{room_name}`/`{room_url}`/`{picks_url}`/`{scores_url}`.

## Local bot container
- **The local `arcaid-bot` container IS a second production bot** if it runs — the repo `.env` holds the prod `DISCORD_BOT_TOKEN`. It re-registers the GLOBAL slash-command set from its stale build on every boot, races prod on every interaction (`DiscordAPIError[40060]`), and answers callouts from the local file (incident 2026-08-21). Its restart policy is `no`; never leave it up alongside prod, and prefer a separate dev bot application for local work.

## Lobby, social, notifications
- **Lobby feed** lives in `lobby_feed_events` (separate from the admin `activity_log`, ADR 0037 — different readers and query patterns). Cursor pagination via `created_at`. WebSocket channel `lobby:${roomId}`. `LobbyFeedGenerator.onScoreSubmitted` is hooked into all score submission paths via fire-and-forget dynamic imports. Lobby config (social links, pinned message, feed settings) stored as JSON in `game_room_settings` keys — no new tables.
- **Friends** use a unidirectional follow model. `FriendsService.getPlayersWhoFriended` is the reverse lookup driving targeted `friend_score` events.
- **`NotificationService.notify`** checks per-user opt-in prefs (`notification_prefs` JSON on `user_preferences`) + in-memory rate limit (5/user/hour). Twelve types, all default-off: `tournamentWin`, `turnToPick`, `tournamentStarting`, `rankDethroned`, `friendScore`, `rotationReady`, `queueLow`, plus the five engagement reminders below. Managed via `/arcaid-notifications` Discord command.
  - `PREF_TYPE_KEYS` is the list — adding one means touching the prefs interface, `PREF_TYPE_KEYS`, `HIGH_VALUE_TYPES`/`WEB_PUSH_TYPES`/`PUSH_TITLES` if applicable, `getPrefsWithExplicit`'s defaults, the Discord `PREF_LABELS` + choice, and `AccountSettings.tsx`'s `NOTIF_TYPES`.
- **Engagement reminders (v2.245.0, E23):** `playReminder`, `halfwayReminder`, `endingSoon`, `inactiveReminder`, `podiumLost` are sent ONLY by `EngagementReminderService.sweep` (Scheduler, every 15 min, clock injectable). Rotation tournaments with `is_active = 1`; never an event, a Throwdown, a paused or finished season. A table's close is the tournament's NEXT rotation. `engagement_reminders` is both the dedupe (row INSERTed before the DM, `UNIQUE(user_id, kind, dedupe_key)`) and the spacing ledger (one reminder DM per player per 20 h across all kinds; `KIND_PRIORITY` picks which); a later-stage reminder also inserts the earlier stages' rows for that game. `podium_sightings` is refreshed for every active game on every sweep, whoever opted in. Recipients are `room_members` (the roster only when `entry_mode` is `invited`; never a banned identity). `playReminderHours` (24/48/72) is a SETTING in the prefs blob, not a `PREF_TYPE_KEYS` entry: read through `playReminderHoursOf`, written through `playReminderHoursUpdate`. A new reminder kind needs its `KIND_PRIORITY` slot and its supersede rule.
- **Milestones** use "exactly equals threshold" count queries — no separate tracking table.
