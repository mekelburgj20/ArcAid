# CLAUDE.md

Guidance for Claude Code working in this ArcAid repository.

## Working agreement

- **Run via Docker.** `docker compose up -d --build` for dev/test/prod. Never suggest `npm run dev` for running the app — `npm run build` and `npm run dev` exist for CI/build verification only.
- **Always build before committing.** `docker compose build` from repo root, plus `cd admin-ui && npm run build` if UI changed. Never push to `main` without a clean build.
- **A UI change means running the ADMIN-UI TEST SUITE too** — `cd admin-ui && npx vitest run` — not just its build and lint. CI runs it; a build-clean UI edit can still fail it. The trap that proves the point (2026-08-25): adding a second encrypted settings field made a document-wide `queryByRole('button', {name: 'Show'})` in `Settings.test.tsx` match the NEW field's reveal toggle, failing an assertion about the iScored one. Build passed, lint passed, CI went red.
- Don't ask permission for `cd`, `git`, or basic file navigation — execute directly.
- **"Resume" ritual:** read `SPRINT_STATUS.md` → read `ROADMAP.md` → `git branch --show-current` → `npm run build` (and admin-ui build if relevant) → present a status summary → continue last session's work.
- For **history**, read `CHANGELOG.md`. For **architectural decisions**, read `docs/decisions/`. For **current work**, read `SPRINT_STATUS.md`. Do not duplicate them here.

## Stack

TypeScript (CommonJS, NodeNext) · Node 24 prod runtime (Playwright noble base; Node 20 in the Docker build stages + CI gate — compiled output is portable) · Discord.js v14 · Playwright · SQLite (NOT `better-sqlite3` — use the package already in `package.json`) · Express v5 · React 19 + Vite (ESM, separate `tsconfig`).

## Architecture

Two sub-applications in one process, served by Express on port 3001.

**Backend (`src/`)** compiles CommonJS to `dist/`. Entrypoint `src/index.ts` boots in order: DB init → load DB settings into `process.env` → clear leaderboard caches → validate env → start API → connect Discord → start `ScoreSyncPoller`.

- `src/engine/` — singletons via `getInstance()`: `TournamentEngine`, `Scheduler`, `ScoreSyncPoller`, `TimeoutManager`, `BackupManager`. Per-use (NOT singletons): `IScoredClient` (Playwright), `IScoredApiClient` (HTTP). Pin-to-scoreboard creation goes through `gameCreation.ts`'s `pinGameToScoreboard()` / `unpinGameFromScoreboard()`; tournament activation goes through `TournamentEngine.activateGame()` / `processSlotMaintenance()`.
- `src/api/` — Express app in `server.ts` mounts four routers: `auth.ts` (login, OAuth, refresh), `rooms.ts` (room-scoped public + admin), `admin.ts` (super-admin), `global.ts` (non-scoped). Middleware in `middleware.ts`: `requireAuth`, `requireRoomAccess(paramName)`, `requireSuperAdmin`, `requireDiscordUser`, `optionalDiscordUser`, `roomVisibilityGate`, `requireNotBanned`. Rate limiters in `rateLimit.ts`. Admin writes auto-audit via `auditMiddleware.ts`. Zod schemas in `schemas.ts`.
- `src/services/` — business logic. Naming is descriptive; `ls src/services/` for the current set. Room-scoped services accept an optional `gameRoomId` parameter for filtering.
- `src/utils/` — `discord.ts`, `terminology.ts`, `cooldown.ts`, `logger.ts` (rotating-file-stream; `formatLogArg` writes `Error.stack` since Error props are non-enumerable and `JSON.stringify(err)` returns `{}`), `secrets.ts` (AES-GCM via `SECRETS_KEY` env), `platformMapping.ts` (canonical platform IDs + aliases — see "Platform stratification" below), `platformRules.ts`, `cronUtils.ts`, `catalogueUtils.ts` (`normalizeGameName`).

**Admin UI (`admin-ui/src/`)** is React 19 + Vite (ESM). All HTTP goes through `lib/api.ts` (relative `/api/` paths — never hardcode localhost). Three layouts: `SuperAdminLayout` (`/admin/*`), `RoomAdminLayout` (`/:slug/admin/*`), `PublicLayout` (`/:slug/*`). Plus standalone global pages (`/scoreboard`, `/games/:id`, `/friends`) — **there is NO public `/catalogue` route**; `GlobalCatalogue` is a super-admin tool under `/admin/catalogue` (public catalogue browsing happens on `/scoreboard`). Room-scoped pages get `roomId/roomSlug/roomName` from `RoomContext`. Public pages get viewer auth from `ViewerAuthContext` (auto-refreshes player tokens within 5min of expiry).

Scoreboard rendering is a Style+Theme dispatch: `SCOREBOARD_STYLE` (banner/showcase/minimal) + `SCOREBOARD_THEME` (showcase variants live in `lib/scoreboardThemes.ts`) → `CardRouter.tsx` selects `BannerCard`/`ShowcaseCard`/`MinimalCard`. Config derivation in `lib/scoreboardConfig.ts`: `deriveScoreboardConfig` is the new path; `deriveCardProps` is the legacy fallback. Live preview on the admin Leaderboard page is rendered inline (CSS scale-transform); the old standalone `ScoreboardPreview` component was removed as dead code in the 2026-08-21 cleanup.

## Multi-tenant model

One DB, many `game_rooms`. Each room has slug, optional Discord guild ID, and per-room settings in `game_room_settings`. Tournaments and ranking groups carry `game_room_id`. `migrateToMultiRoom()` in `database.ts` runs idempotently on startup.

**Auth roles:** `super_admin` (server-wide), `room_admin` (per-room — password, invite, or Discord), `player` (Discord-authenticated non-admin), guest (no token). Player tokens live in `arcaid_player_token` localStorage, separate from admin tokens.

**Discord OAuth state encoding:** `__super__` → super-admin login, `player:<slug>` → public-page player login, bare slug → room admin login. Scope must be `identify` only — `guilds.members.read` causes 400s on the authorize redirect.

**JWT refresh tokens** stored in `sessions` (30d expiry). Frontend `api.ts` auto-refreshes within 5min of access-token expiry and retries on 401 before redirecting to login.

**Per-room Discord/iScored credentials** live in `game_room_settings`: `DISCORD_GUILD_ID`, `DISCORD_ADMIN_ROLE_ID`, `DISCORD_ANNOUNCE_CHANNEL_ID`, `ISCORED_USERNAME`, `ISCORED_PASSWORD`, `ISCORED_GAMEROOM`, plus `DISCORD_ENABLED` / `ISCORED_ENABLED` toggles. The bot token + Discord client ID/secret stay global. **Slash commands are guild-scoped (v2.120.1):** reads (`/list-active`, `/list-scores`, `/list-winners`, `/view-queue`, `/view-stats`) and the tournament-id admin commands (`/run-cleanup`, `/nominate-picker`, `/pause-pick`) resolve `resolveGuildReadScope(interaction.guildId)` in `src/utils/discordRoomFilter.ts` — rooms whose `DISCORD_GUILD_ID` is the invoking server, minus Discord-off/approval/suspended rooms; legacy env-guild fallback covers settingless rooms; no link or DM → ephemeral not-linked reply, nothing shown. Writes resolve their room via `discordWriteTarget.ts`. **Any new command that reads or mutates room data must go through one of those two** — a bare `FROM tournaments`/`FROM games` in a command is a cross-room leak. Known residue: `StatsService.getGameStats`/`getPlayerStats` and the five tournament/game autocompletes are still cross-room (queued).

## Score system & identity

- `submissions` is the source of truth for *best-per-player-per-game*. ID format `${gameId}-${username.toLowerCase()}` (sync-compatible with iScored).
- `score_history` logs every score event with source tracking. **It is the physical union of all score sources**: community/freeplay submits dual-write into it via `ScoreHistoryService.log` (`source='community'`, from `CommunityScoreService.submitScore`), so room-wide "all scores" reads (e.g. `RoomScoresService`) read `score_history` ALONE — never UNION `community_scores` (the admin wipe-player path deletes `score_history` rows but deliberately NOT `community_scores`, so a union would resurrect wiped scores). **Tournament leaderboards read `score_history` filtered by `submitted_during_tournament_id`** (best-during-window wins) — `submissions` is still written for back-compat. The submit-moment "You are #N of M" card (`ScoreRankService.computeRoomRank`, v2.125.1) ranks against that SAME window population when the game is ACTIVE in a tournament — never against a source-filtered subset (the pre-fix `source='tournament'`-only union hid every synced rival). As of v2.8.0, `LeaderboardService.recalculate()` partitions by `COALESCE(submitted_by_user_id, 'iscored:' || LOWER(iscored_username))` so multi-alias Discord users collapse to one row per game; pure-anon rows still partition per-name.
- **One resolver decides which game a web score belongs to (v2.155.1).** `SubmissionGameResolver.resolveSubmissionGame` orders: an explicit `gameId` (the card the FE knows the player pressed "Submit" on) when it matches the room/name/status → else the name lookup, EARLIEST-`start_date` ACTIVE row wins among same-named games (WARN naming every competitor) → else the newest COMPLETED row. `submit-score`, `freeplay-score`, the legacy `community-scores` route, the OAuth draft commit, and `ScoreHistoryService.log`'s tournament auto-resolve all call it ONCE per request (event gate → resolver → provenance check → write), and the result is threaded into everything downstream **(v2.155.2)**: `GET /submit/platforms` (the sheet sends the card's `gameId`), `ScoreProvenanceService.validateForRoomGame`, `ScoreRankService.computeRoomRank`, `IScoredSubmitSync` (which board a web score mirrors to) and `RotationNudgeService` — so the picker, the acceptance check, the `submissions` upsert, the `score_history` stamp, the cache invalidation and the rank card all describe the SAME game. A second ad hoc name lookup in any submit path is the ambiguous-active-games bug (two ACTIVE same-named games in different tournaments) reborn — route it through the resolver instead. **`ScoreHistoryService.isDuplicate`'s dedup key includes `submitted_during_tournament_id` as of v2.155.3** — one play may be submitted to EACH tournament currently running the table, so the same score into a DIFFERENT tournament lands on both boards, while the same score into the SAME tournament is still a re-send and gets dropped.
- **Three-table identity layer** (v2.8.0):
  - `user_mappings(discord_user_id, iscored_username UNIQUE COLLATE NOCASE, avatar_hash, created_at)` — **many-to-one**: one Discord user can hold many iScored aliases. UNIQUE on iscored_username (case-insensitive) so one alias maps to at most one Discord user. `discord_user_id` PK was dropped in migration 095.
  - `user_profiles(discord_user_id PK, display_name, avatar_hash, avatar_fetched_at, ...)` — one row per Discord user. Holds the user-chosen global display name (case-insensitively unique via partial UNIQUE INDEX `idx_user_profiles_display_name`) plus the avatar cache (moved off `user_mappings.avatar_hash`, which still exists but is no longer the read source).
  - `anonymous_identities` / `anon_room_claims` / `room_members` — pre-existing per-room claim tables; unchanged.
- **Display resolution rule.** Everywhere a player name renders: `display_name ?? iscored_username`. FE has a centralized `playerName(entry)` helper exported from `admin-ui/src/components/ScoreboardComponents.tsx`. BE responses ship both fields; matching/keying logic still uses `iscored_username` (stable identifier, used in URL routes like `/players/:name` and React `key` props).
- **Forward attribution at merge.** `MergeService.recordMerge` writes `user_mappings(discord_user_id, iscored_username)` inside the transaction with a pre-flight `MAPPING_CONFLICT` check; `ScoreSyncPoller` picks it up on the next poll cycle (load is fresh per cycle at `ScoreSyncPoller.ts:109`). `reverseMerge` deletes that alias row and re-anonymizes any post-merge auto-attributed rows (rows that weren't in the snapshot but landed under the auto-mapping rule between merge and reversal — special-cases `global_scores.player_id` vs the other tables' `discord_user_id`). `MergeService.previewMerge` derives the tournament-completed timestamp from `MAX(games.end_date) WHERE status='COMPLETED'` (no `tournaments.end_date` column exists).
- **First-claim-wins names per room.** `RoomNameClaimService.resolveAndClaim` walks a suffix loop (`Bob` → `Bob_2`); `checkAvailability` is the pre-submit dry-run used by `SubmissionSheet`. Discord claims live in `room_members.display_name`; anon claims in `anon_room_claims` (one anon-token may hold multiple names per room). The room-scoped `room_members.display_name` is **separate** from the global `user_profiles.display_name` — the former is per-room first-claim policy, the latter is the user-chosen global rendering name. Merge does NOT touch `room_members.display_name`.
- **Anon ID:** `x-user-id` header carries a `localStorage` UUID for guest write paths (community scores, comments). Used for comment author-only delete.
- **EVERY score reaches the Global Scoreboard unless the player opted out (v2.153.0, ADR 0023).** Tournament, event round, Throwdown, AtGames cabinet and VPXS cabinet all fan out; **format never decides, the player does** (`user_preferences.share_to_global`, default on, with the per-submission checkbox still winning for one score where a form exists). The three paths with NO submit form go through ONE helper, `GlobalScoreService.fanOutAutomatedScore` — it resolves the account preference (`resolveExcludeFromGlobal`) and refuses a null/unlinked identity; a fourth caller that hand-rolls either check is a bug. **`'sync'` remains the ONE refusal** and is about missing provenance, not format (ADR 0016 P2 §3b forces `unknown`/`unknown`, which cannot be placed honestly on an engine-split board) — enforced INSIDE the fan-out so a call site cannot reinstate it. Rooms keep their own `GLOBAL_SCOREBOARD_ENABLED='false'` switch; that is the room owner's decision, not the player's.
- **Global scoreboard fan-out gate:** `GlobalScoreService.fanOutFromRoomSubmission` early-returns when `normalizeSubmitterUserId` is null — guest submissions never appear on `/scoreboard`. As of v2.60.0 (ADR 0016 P2) the method takes a **required `source` param and rejects `'sync'`** — iScored-synced scores never reach the Global Scoreboard (they stay fully visible on room leaderboards); the old `iscored:*` synthetic-ID fan-out from `ScoreSyncPoller` is removed. Synced scores are always `engine='unknown'`/`device='unknown'` — no inference, ever (`tournaments.iscored_default_engine`/`_device` are vestigial and unread).
- **Login is unconditionally mandatory for all web score submissions (v2.79.0); the per-room `REQUIRE_DISCORD_LOGIN` setting and `conditionalRequireDiscordUser` middleware were retired wholesale in v2.80.0** (migration 138 deleted stored rows; `OrphanService` deleted — existing `orphaned_at` rows and every `orphaned_at IS NULL` query filter remain untouched). Comments/tips stay guest-open via `optionalDiscordUser`. Membership/privacy is governed by three orthogonal room settings: `ROOM_LISTED` (default on; `'false'` drops the room from `GET /api/rooms` only — direct URL, portal, and member `/api/me/rooms` visibility unaffected), `JOIN_POLICY` (`open`/`approval`), and `AUTO_APPROVE_GUILD_MEMBERS` (approval rooms auto-approve join requests from linked-guild members via `JoinRequestService.tryAutoApprove` — identity-link-aware, bot-side `isMemberOfGuild` check, any uncertainty degrades to the manual queue, never auto-deny; audit row `resolved_by='auto:guild'`).
- **`/map-user` Discord command is additive (v2.8.0).** It adds an alias for the target Discord user; errors if the name is already mapped to a different user. The legacy "replace" semantic is gone (no `/unmap-user` companion shipped — deferred). The `user_mappings` writers are `global.ts` (global-submit display-name claim), `mapuser.ts`, `submitscore.ts` — all `ON CONFLICT(iscored_username) DO NOTHING` (was `ON CONFLICT(discord_user_id) DO UPDATE`) — plus `MergeService.recordMerge` (pre-flight `MAPPING_CONFLICT` check inside the txn). **Discord OAuth login writes NO mapping** (verified 2026-07-15; an earlier revision of this list wrongly included `auth.ts`): a logged-in web player gets `submitted_by_user_id` attribution on their scores and a per-room `room_members.display_name` claim, but their room name is NOT a global alias until `/map-user`/merge links it — name-based stat resolvers (compare, enhanced player stats) read `user_mappings` only.

**Alias-link effects are centralized (v2.127.0).** `src/services/IdentityAliasEffectsService.ts` is the ONE place that knows what happens when an iScored alias becomes linked. **Every `user_mappings` writer must call `onAliasLinked(userId, name)`, gated on the INSERT actually inserting (`res.changes`, since they all `DO NOTHING`); every alias REMOVAL must call `onAliasUnlinked`** — currently `IdentityClaimService.claim`/`approve`/`releaseAlias`, `mapuser.ts`, `submitscore.ts`, `global.ts` and `MergeService.recordMerge`. It (a) folds synthetic `iscored:<Name>` `room_members` rows onto the real account (earlier `joined_at` wins, display name carried over when the real row lacks one), (b) re-attributes the unowned SYNCED rows in `score_history` + `submissions` across ALL rooms — `submitted_by_user_id IS NULL AND discord_user_id LIKE 'iscored:%' AND merged_from_anonymous_identity_id IS NULL`, minus a **freeze gate** that skips rows whose `submitted_during_tournament_id` names a COMPLETED (`is_active = 0`) tournament, exactly as `MergeService.previewMerge` does — and (c) fire-and-forget `UserProfileService.hydrateFromDiscord`. `community_scores`/`global_scores` are never touched (sync writes neither). (a)/(b) run in the caller's transaction when a `db` handle is passed and their errors propagate; (c) never can. Re-attribution invalidates Leaderboard + GlobalLeaderboard **+ Ranking** via the shared `invalidateIdentityCaches` — the ranking watermark is over counts/sums, which re-attribution doesn't change. Hydration (also a nightly `20 4 * * *` sweep, `refreshStaleDiscordProfiles` — whose candidates are `user_profiles` rows with a stale/NULL stamp UNION Discord-snowflake ids in `user_mappings`/`room_members` that have NO profile row, so a link-time hydration failure is retried) is one `fetchDiscordUser` REST call, skips Google ids and anything fetched inside 24h, fills `username` only when NULL, never touches `display_name`, and is killed by `PROFILE_HYDRATION_ENABLED='false'`. **The AUTOMATIC avatar provider is Discord-first as of v2.127.1** (`resolveEffectiveAvatarProvider`: explicit preference → Discord `avatar_hash` → Google URL → none) — the original Google-first rule was really "Google always", because Google returns a generated letter tile rather than NULL for a photo-less account; migration 160 re-derived the preference-less rows. **`room_members` never holds an `iscored:*` id any more** — migration 159 folded/purged the survivors and `RoomMembershipService.isRealUserId` now rejects the prefix.

**Display-name resolution in BE leaderboard queries.** **`submitted_by_user_id` never holds the poller's synthetic `iscored:<name>` id** — `normalizeSubmitterUserId` (v2.125.2) returns null for it, because every resolver keys `user_profiles` on that column first and only falls back to `user_mappings` when it is NULL; a synthetic value there hid the avatar/name of anyone who linked AFTER their scores synced (Wyo, 2026-08-21). `PlayerProfileResolver` additionally treats a synthetic value as absent for cached rows. Every leaderboard/ranking/stats query that ships `display_name` to the FE resolves the same way: `user_mappings` for the `iscored:*` synthetic-id fallback, then `user_profiles` keyed on `COALESCE(submitted_by_user_id, um.discord_user_id)` — deliberately NOT on the raw per-row discord id. Live (uncached) queries express it as two LEFT JOINs: `RankingService.computeRankings` (two batched lookups, same rule), `StatsService.getAllPlayerStats`/`getRoomOverview`, `GlobalLeaderboardService.getTopScoresForCards`, `/api/global/recent-scores`.

**As of v2.74.0 (S24.1) the CACHED paths resolve at READ time, not at recalculate time.** `leaderboard_cache` and `global_leaderboard_cache` store identity-stable rows only (`submitted_by_user_id`, the raw per-row discord id, `iscored_username`, score, provenance) wrapped in a `{v, rows}` envelope; `resolveProfiles` in `src/services/PlayerProfileResolver.ts` attaches `display_name`/`avatar_hash`/`avatar_url` in two batched queries per page. **Never bake a name or an avatar back into that cache JSON** — doing so re-creates the profile-edit invalidation storm (`invalidateAll()` is a whole-table DELETE, after which `getActiveLeaderboards` serially recalculates the whole room) and the bug where an avatar change never reached the Global Scoreboard at all. The rename (`users.ts`) and avatar-change (`auth.ts`) paths consequently perform NO cache invalidation; the settings/merge/admin `invalidateAll` sites are unrelated and still required. A blob in the old bare-array shape is treated as a cache miss.

All web submission paths (`/submit-score`, `/freeplay-score`, `/community-scores`) sync via `IScoredSubmitSync.syncScoreToIScored()` — single helper, divergence not possible. `IScoredApiClient.submitScore` parses response text before `JSON.parse` to handle "Access Denied" plain-text rejections.

**Score CORRECTION is not moderation (v2.149.0).** `PATCH /:roomId/score-history/:historyId/score` → `ScoreHistoryService.correctScore` changes a score's VALUE in place. **Three tiers as of v2.150.0** (`requireDiscordUser`, matching the sibling per-row DELETE): super_admin → any row; room_admin → any row in their rooms; **the SUBMITTER → their own row while the card is UNLOCKED**. Owner ruling 2026-08-31 (v2.149.0 shipped admin-only; this reverses it). **"Locked" = the game is no longer `ACTIVE`** — `ownerCorrectionWindow`, which is the SAME line `isCooldownLocked` draws for submissions and what both admin lock affordances change; do NOT add a `games.locked` column, it would be a second drifting answer. The ACTIVE game is matched by (room, name) AND the row's `submitted_during_tournament_id` must match its tournament, or a table rotating back round re-opens the PREVIOUS run's scores. An admin-**verified** row is closed to its owner (the badge would otherwise sit on a value nobody checked); admins are never blocked. Ownership is the RAW `submitted_by_user_id`, so a synced row belongs to nobody. It moves the `community_scores` twin and the `global_scores` fan-out with the row (same conservative exactly-one match rules as `deleteEvent` — extracted into `findCommunityScoreTwinId`/`findFannedOutGlobalScoreId` so the two paths cannot drift), recomputes the `submissions` best-per-player row, invalidates + broadcasts. It writes **no tombstone on the corrected row**, deletes no photo, and fires **none** of the submit-time side effects (no lobby event, no toast, no notification, no announcement) — a correction is bookkeeping, not a new score. **The one exception: a correction DOWNWARD tombstones the OLD value**, because `IScoredApiClient` can submit but cannot edit or delete, so on a mirrored room `ScoreSyncPoller` would re-import the old higher score within a cycle and silently undo the fix; the cost is that a later genuine score between the new and old values is suppressed until an admin clears it. **That guard is skipped when the room resolves to NO iScored creds** (`roomSyncsToIScored` → `getIScoredCredsForRoom`, the SAME resolution the poller uses to decide whether to poll, so "switched off" / "partially configured" / "no env fallback" can never disagree between the two; a NULL room — a Throwdown — is never synced, and a settings-read failure degrades to "it might sync" and KEEPS the tombstone). `deleteEvent`'s tombstone stays UNCONDITIONAL on purpose: there the row is gone, so a stray suppression is the cheaper mistake. **Correction must sit wherever a score DELETE sits** — adding one to a new surface without the other is the bug that took three releases to stop recurring (v2.149.1, v2.150.0, v2.150.1). The shared dialog is `components/CorrectScoreModal.tsx`; the surfaces are the Game Detail board rows and per-player history rows, the admin Leaderboard's Manage Scores modal, and `GameQuickView`'s ranked rows + nested history rows (v2.150.1 — `QuickViewTarget.gameStatus` exists solely to feed the owner tier's locked check). **Deliberately excluded:** `GlobalGameDetail`'s delete, which acts on `global_scores` via `DELETE /api/me/global-scores/:scoreId` and is one-way by design — a correction there would desync the global copy from the room row it fanned out from (which goes through `api.*` for the admin token — the public page deliberately uses a raw fetch with the player token so a 401 can't bounce a player to the super-admin login). **The board-row pencil is NOT hover-gated**, same as the row delete: v2.149.0 shipped it only inside the history expand, which is gated on `hasMultiple`, so a player with one score on a game had no reachable correction at all. Manage Scores needs `history_id` on `GET /:roomId/leaderboard/:gameId/submissions` — matched on an EXACT score (not "the player's best") and joined by (room, name) since `game_id` is NULL on modern web rows; no match → NULL → no pencil. Born from the 2026-08-30 incident: `66,661,589,860` typed for `6,666,158,980` on a table that had already rotated to COMPLETED, where deleting would have tombstoned the WRONG value, dropped the player to a previous best that handed the win to someone else, and left no way back in (every submit path requires `games.status = 'ACTIVE'`).

**Per-row score moderation (v2.9.0).** Two delete paths, both gated server-side and emitting `leaderboard:updated` globally on success.
- **Admin "wipe player from game"** — `DELETE /api/rooms/:roomId/admin/games/:gameId/submissions/:submissionId` (`requireAuth + requireRoomAccess`). Drops the `submissions` row + every matching `score_history` row for `(game_room_id, lower(iscored_username), game_id-or-game_name)`. Works on pinned games (LEFT JOIN tournaments + `ownedByRoom` check; pre-v2.9 the INNER JOIN 404'd pinned rows). Surfaced via `ManageScoresModal` (admin Leaderboard page → "Scores" button on each card).
- **Per-row delete (admin or self)** — `DELETE /api/rooms/:roomId/score-history/:historyId` (`requireDiscordUser`). Authorization tiers: super_admin → any row; room_admin → any row in their rooms; player → only rows where `submitted_by_user_id === viewer.discordId`. Restricted to `source IN ('tournament','sync')`. After delete, recomputes the corresponding `submissions` row from remaining `score_history` (`ORDER BY score DESC, created_at ASC LIMIT 1`); deletes if none left, else updates `score`+`timestamp` to the new top row's values. Surfaced as a hover-only trash icon on each row in the `GameDetail.tsx` per-player history expand.
- **`deleted_score_suppressions` tombstone (migration 096).** iScored has no per-score delete API. Without help, `ScoreSyncPoller` would re-import the deleted score on the next ~30s cycle. Both delete paths write `(game_id, lower(iscored_username), suppressed_score)` with `MAX(existing, deleted_score)` on conflict. The poller bulk-loads suppressions per game and skips `score <= suppressed_score` before its existing `> existing.score` check — new higher scores still flow through, deleted scores stay deleted. iScored-side cleanup remains manual (ROADMAP).

## iScored integration

`IScoredApiClient` (HTTP, fast) is the default for score read/write. `IScoredClient` (Playwright) is required for game management — hide/create/delete — and is the fallback when the API can't satisfy a call. `ISCORED_API_ENABLED` gates the path. `ScoreSyncPoller` runs continuous background sync (default 10s tick) with pause/resume during maintenance. Settings hot-reload through `SettingsService`.

**Per-account session serialization (v2.10.0).** Every Playwright iScored mutation goes through `IScoredSessionRegistry.withSession(creds, fn)` — a singleton in `src/engine/IScoredSessionRegistry.ts`. Calls for the same iScored account chain serially: only one `fn` runs at a time per account. The underlying client is held across calls within a 1.5s idle TTL so cron-fire batches reuse the same Playwright login. **`new IScoredClient(...)` is allowed only inside the registry's `acquireClient` method** — every other call site (TournamentEngine, TimeoutManager, gameCreation, IScoredSubmitSync, the four rooms.ts admin endpoints, the four Discord commands, the admin backup endpoint) acquires sessions via the registry. Pre-v2.10 each call site constructed its own client; on rtx_pinball's Wed 22:00 fire (4 weeklies + DG sharing one account) this caused dropdown-state-flip contention — `IScoredClient.deleteGame` short-circuited at line 692 with `Game '<name>' not found in dropdown. Skipping delete.` and the local DB went HIDDEN while iScored kept the entry visible. See ADR 0012.

**`deleteGame` returns `Promise<boolean>`.** `false` on the dropdown short-circuit (entity not found), `true` on completed delete. Callers (`runCleanup`, `deleteGameCompletely`, the rooms.ts admin endpoints) branch on the result and log accurately. Pre-v2.10 the method returned `void` and callers logged `Deleted from iScored: <name>` regardless — failure was indistinguishable from success.

**Notification-gated polling (v2.10.0).** Each tick fetches iScored's static `/notifications/rooms/room_<roomID>.txt` per account; the expensive `getAllScores` call only fires when the body changed (or the 10 min backstop elapsed). `IScoredNotificationGate` owns the cache + decision. roomID is auto-discovered from the public `roomCommands.php?c=getRoomInfo&user=<slug>` endpoint at first poll (not under `/api/`, undocumented but used by iScored's own room iframe); `ISCORED_ROOM_ID` env overrides for the env-fallback account only. Discovery failure → one-time WARN + degrade to backstop-only polling for that account. Backstop interval configurable via `ISCORED_API_POLL_BACKSTOP_MS` (default 600000). Background: Daniel Reynolds (iScored) → Justin, 2026-04-29: 500K queries/month vs. 10 actual scores entered prompted the change.

**iScored room snapshots (v2.117.0).** iScored has no undo, so every destructive iScored path snapshots the room first: `IScoredSnapshotService.captureBeforeMutation(client, creds, reason, roomIds)` is called INSIDE the existing `withSession` callback (reuses the session, no extra login) at `runMaintenanceInternal`, standalone `runCleanup`, `deleteGameCompletely`, `unpinGameFromScoreboard`, both admin game deletes and the reconcile POST. It never throws into the caller (ERROR log, mutation proceeds) and is debounced per account (`creds.username` lowercased, 10 min default) so a multi-tournament cron wave writes one file. **Add the hook to any new path that calls `deleteGame`** — lock/hide toggles are reversible and deliberately unhooked. Snapshot = `data/iscored-snapshots/<gameroom>/<ts>.json`: games with hidden/locked/tags via `getGamesOnIScored()` + scores via the public `getAllScores` (shared normaliser `normalizeIScoredScoreResponse` in `src/utils/iscoredScores.ts`); no photos/styles/score ids. Nightly 04:00 sweep + 30-day prune in `Scheduler.startIScoredSnapshotCron`; super-admin list/snapshot-now/download/delete/restore on `/admin/backups`. Restore recreates only games MISSING on iScored (name-matched, apostrophes stripped), replays per-player bests while the game is open, then applies hidden/locked, and re-links `games.iscored_id` old→new — dates and ids are not preservable (the API accepts name+score only). **Under vitest the capture is inert unless the test calls `setRootForTests`** — unrelated maintenance tests otherwise reach the real iScored API with `.env` creds. Settings `ISCORED_SNAPSHOTS_ENABLED` (default on) / `ISCORED_SNAPSHOT_DEBOUNCE_MS` / `ISCORED_SNAPSHOT_RETENTION_DAYS` — env or global settings, no UI.

**Per-room delete kill-switch (v2.120.0).** `ISCORED_ALLOW_DELETE='false'` in `game_room_settings` means NO code path may `deleteGame` on iScored for that room (`iscoredDeletesAllowed(roomId)` in `src/utils/iscoredCreds.ts`, checked BEFORE any session is acquired at all seven `deleteGame` call sites — cleanup archives locally only, deleteGameCompletely/unpin/admin removes report `iscoredStatus:'skipped'`, sync-iscored `delete` + Reconcile POST 409). Lock/hide/create/submit/reorder are unaffected. **Any new `deleteGame` caller must check it** (and add the snapshot hook). Exists because rooms can bridge to an iScored board they don't own (rtx_pinball → the RTX group's `RTX_Pinball` room, 2026-08-20) — their historical boards must survive Arcaid's cleanup rules.

**Deactivate vs. Delete (v2.7.x).** Two distinct admin actions on an ACTIVE game, both surfaced on the Tournaments admin page:

- **Deactivate** — `TournamentEngine.deactivateGame()` and `processSlotMaintenance()` (cron rotation). End-of-round semantics. Steps: (1) `finalSyncScoresForGame()` pulls iScored scores into `submissions` + `score_history` so anything submitted between the last poll cycle and this call is captured, (2) `setGameStatus({ locked: true })` on iScored (skipped as `'shared'` when another ACTIVE row owns the same `iscored_id`), (3) mark COMPLETED — `iscored_id` is intentionally KEPT non-NULL so `runCleanup`'s retain/scheduled/immediate policies can still find the row.

- **Delete** — `TournamentEngine.deleteGameCompletely()` exposed at `DELETE /api/rooms/:roomId/games/:id`. Destructive variant for "wrong game in wrong tournament". Steps: (1) final sync (same as above), (2) `deleteGame()` on iScored (also `'shared'`-guarded), (3) orphan local scores (`UPDATE submissions/score_history SET game_id = NULL` and `global_scores SET origin_game_id = NULL` per ADR 0005), (4) `DELETE FROM games`. Score *records* are kept so the player's personal history is preserved, but the games row and its leaderboard are gone.

The duplicate-DM bug (WHO dunnit / rtx_pinball incident, 2026-04-27) is killed by the SyncPoller's `ORDER BY` (status pref then `created_at DESC`, see `ScoreSyncPoller.pollOneAccount`) — even when legacy rows share an `iscored_id`, the poller deterministically picks the ACTIVE one and matches the existing `submissions` row by id. `finalSyncScoresForGame` is shared by both Deactivate and Delete; it never fires `LobbyFeedGenerator.onScoreSubmitted` (data capture only, no live events).

## Catalogue (global_games)

- **4-step dedup hierarchy** in `GlobalGameService.upsert`: (1) external ID match (`opdb_id`/`vps_id`/`igdb_id`, with cross-type guard), (2) IPDB URL cross-reference for pinball, (3) reserved, (4) normalized-name match (full-table scan + JS-side `normalizeGameName` — no SQL `LIKE` because punctuation broke it). Step 4 is two-tier: **concrete** matches (both sides have non-null mfg + year, exact match) outrank **loose** (NULL-tolerant). Tie-break: external-ID count → mfg/year populatedness → oldest `created_at`.
- Composite UNIQUE INDEX `idx_global_games_identity` on `(LOWER(name), type, LOWER(COALESCE(manufacturer,'')), COALESCE(year,0))`. Same-name pinballs from different manufacturers coexist; true `(name, type, mfg, year)` dupes reject. See ADR 0004.
- **Library = global catalogue.** As of v2.6.0 the legacy `game_library` table is dropped (migration 092). Tournament activation, the per-room library page, autopick, Discord autocomplete, and leaderboard image fallback all read from `global_games WHERE status='approved'` directly. See ADR 0007.
- **`game_room_game_library` survives** (post-v2.6.0) for one purpose only: per-game style overlay (`catalogue_style_id`, `logo_style_id`, `bg_style_id`, `style_header_disabled`) keyed on `(game_room_id, game_name)`. The `custom_platforms` and `display_name` overlay columns are unread (column kept for now). Future cleanup will re-key the surviving overlay onto a `(game_room_id, global_game_id)` table and drop this one too.
- **Per-room game tags** live in a separate table `room_game_tags(game_room_id, global_game_id, tag)` — variant-keyed via `global_games.id`. Game's effective platforms = catalogue platforms ∪ room tags. UNION applied across `ensurePlatformAllowed`, `/api/submit/platforms`, `/:roomId/platforms/available`, library list response, web pick-game, admin activate-game, Discord activate/pick autocomplete, autopick paths. `RoomGameTagsService.getTagMapByGameNameForRoom` is the batched-lookup helper. Migration 093. See ADR 0008.
- **Pending-approval flow:** room admins propose new globals via `POST /:roomId/game_library/submit_to_global` (`status='pending'`); super-admins approve/reject/merge at `/admin/catalogue/approvals`. Public `GET /global/games` hard-codes `status='approved'`.
- **`GlobalGameService.findCandidates(input)`** is the read-only dedup walker (extracted from `upsert`'s hierarchy) powering the per-room contribution proposal endpoints.

## Catalogue importers

Each importer feeds the same `GlobalGameService.upsert` path so the dedup hierarchy keeps the catalogue clean. Admin endpoints under `/api/admin/catalogue/sync-<source>`; FE buttons on `/admin/catalogue`.

- **VPS** (Virtual Pinball Spreadsheet) — primary pinball metadata source. Fetches the VPS database JSON, splits into `playable` + `cataloguable` filters, downloads images. Background image-download pass after the metadata pass returns.
- **VPXS Wizard** — README parser, splits `wizard_auto` (verified VPXS) from `wizard_manual` (Manual Install Tables). Tags `vpxs` vs `vpxs_manual` accordingly.
- **OPDB** — pinball metadata + manufacturer/year data. Requires `OPDB_API_KEY` env var.
- **IGDB** — arcade/console games via Twitch OAuth. Requires `TWITCH_CLIENT_ID` + `TWITCH_CLIENT_SECRET`.
- **Steam Pinball** — Zen + Zaccaria DLC catalogues across six Steam apps. `tmp/pack-contents-draft.md` source-of-truth → `src/services/steamPinballPackContents.ts` (committed). Curated `PACK_CONTENTS` map expands DLCs into per-table upserts. v2.5.0.
- **FX VR** — Pinball FX VR (Meta Quest standalone) catalogue tagger. `tmp/fx-vr-tables-draft.md` (gitignored) → `tmp/emit-fx-vr-data-ts.js` → `src/services/fxVrPackContents.ts`. 39 tables across 17 packs. Tags `pinball_fx_vr`. v2.7.0.
- **AtGames** — two unauthenticated sources, no API key. `AtGamesApiClient` walks AtGames' own catalogue feed (`atgames.net/api/leaderboards/games`, CURSOR pagination via `after`/`nextAfter`, 8 rows/page; `limit`/`page`/`catalog`/`rule`/`table` are all silently ignored) for canonical names, `hardware_models`, and the stable `game_id` → `global_games.atgames_id`, which makes AtGames dedup a **step-1 external-ID match**. `AtGamesEStoreClient` reads AtGames' Shopify storefront (`atgames.us`) for `studio`. Tags `atgames` + one `atgames_<variant>` per cabinet (HD/4K/Micro/HDP/ALU/Mini/Gamer/Core) derived from `hardware_models`. Replaced the Google Sheet in v2.112.0.
  - **The feed mixes pinball and arcade** and says which nowhere — the importer classifies on pinball-exclusive cabinet codes (`RK9920`/`HA9919`/`HA8818`/`HA8819C`). Shared codes can't discriminate: an arcade ROM lists `HA8819` "Legends Pinball" too. Add any new pinball cabinet to `PINBALL_ONLY_MODELS` or its exclusive tables silently stop importing.
  - **Studio attribution is five tiers, strongest evidence first:** pack contents list → series parenthetical → pack-title prefix → announced brand → `src/services/atgamesStudioOverrides.ts` (curated, LAST so the store always wins). 100% coverage. The first four generalise to future packs; the curated map does not, so **every sync logs the names of unattributed tables** — that WARN is the maintenance trigger for the override file. It fires mainly for ANNOUNCED-BUT-UNRELEASED tables: AtGames puts a table in the feed weeks before it has a store listing, so the fix is usually an interim override entry from AtGames' Originals release schedule, which goes inert once the table ships.
  - **`studio` is NOT `manufacturer`.** FarSight publishes Gottlieb machines, Magic Pixel publishes Zaccaria, Zen publishes Williams. Putting a studio in `manufacturer` makes `manufacturerYearAgree` compare "magic pixel" to "zaccaria", fails step-4 dedup, and inserts a duplicate on every sync — the exact class repaired by the 88-row prod merge. Manufacturer is landed out-of-band via `GlobalGameService.fillMissingManufacturer` (gap-fill only, never in the upsert input, so dedup matching is unaffected).

## Platform taxonomy

**Two taxonomy generations coexist.** The provenance taxonomy (ADR 0016) lives in `src/utils/scoreProvenance.ts` (BE) mirrored **byte-identically below the header** in `admin-ui/src/lib/scoreProvenance.ts` (locked by `scoreProvenance-parity.test.ts` — extend, never weaken): `CANONICAL_ENGINES`, `CANONICAL_DEVICES`, `ENGINE_DEVICE_COMPAT`, `LEGACY_PLATFORM_MAP` (every canonical engine id is an identity key as of v2.62.0), and `foldCataloguePlatforms` (the ONE legacy→engines+features fold shared by migration 129 and all seven importers — never fork it). ## Pin-to-scoreboard

`games.tournament_id IS NULL` is the canonical pinned-row signal. `games.game_room_id` is denormalized (equals `tournament.game_room_id` for tournament rows; set explicitly for pins). Unique partial index `idx_games_pinned_unique ON games(game_room_id, LOWER(name)) WHERE tournament_id IS NULL` prevents double-pin per room. **Cascade on unpin is application-level, NOT `ON DELETE CASCADE`:** `UPDATE submissions SET game_id = NULL` (and same for `score_history` + `global_scores.origin_game_id`) before DELETE — keeps history. See ADR 0005.

## Live Event format (v2.135.0, ADR 0017)

`tournaments.format` is `'rotation'` (everything that existed before) or `'event'`. An event is time-boxed: N rounds, each ONE `games` row pre-created with `round_no` + `scheduled_start_at`/`scheduled_end_at` and the NEW status **`SCHEDULED`** — deliberately not `'QUEUED'`, which 16 non-test files consume (pick queue, TimeoutManager, the `queue_order` backfill, reconcile). Rounds are `games` rows so all ~15 existing `games`+`tournament_id` readers work unchanged.

- **Events register NO cron.** `cadence = {"timezone": tz}`; `Scheduler.scheduleTournament` skips a cadence without `cron`, which is what keeps `runMaintenance`/`processSlotMaintenance`/`TimeoutManager` from rotating rounds out from under the schedule. The clock is `EventScheduler.tick()` (`src/engine/EventScheduler.ts`), a per-minute task registered beside the timeout checker. Stateless + at-least-once safe: every flip is `UPDATE … WHERE status = <expected>` acted on only when `changes === 1`, every announcement is guarded on an idempotency stamp (`checkin_announced_at`, `event_finished_at`). **The status flip precedes iScored board creation** — a bad-creds Playwright login costs ~40s and the tick is reentrancy-guarded, so board-first would hold the round shut and delay the next minute too.
- **`EventSubmissionGate.checkEventSubmission` is THE one enforcement point** — called before ANY write by the three web submit routes and Discord `/submit-score`. A new submit path means a new call site; skipping it makes every window in that room advisory. **Precedence (an event never shadows rotation):** ACTIVE event round wins → else a SCHEDULED round gates ONLY when no rotation game of that name is ACTIVE in the room → else full passthrough. `EventService` also refuses the name clash at save time, but a rotation can activate the name later, so the runtime rule is the backstop. **`ScoreSyncPoller` is not gated** (synced scores have no play time); they're filtered out of standings instead.
- When the gate returns an `event`, the caller MUST thread `tournamentId` + `gameId` into `ScoreHistoryService.log` — that stamp is the only thing keeping two rounds of the same table apart.
- **One grace, one helper.** `tournaments.end_grace_sec` (default 60; exit-to-submit hosts use 120-180) is resolved by `eventEndGraceSec()` in the gate module and used by BOTH the gate's accept window and the scheduler's close step. Never hand-copy the default.
- **Check-in identity is canonical** (`IdentityLinkService.resolveCanonical`) on both write and read, or a Google check-in won't match a Discord submit. Check-in closes at round 1 start (no separate column); `source='admin'` is the straggler path and deliberately bypasses the late-check-in guard.
- **`event_result` is identity-stable rows ONLY** — same doctrine as `leaderboard_cache`; never bake a name or avatar in, `resolveProfiles` attaches them at read. Finishing sets `is_active = 0` so the alias-link freeze gate treats it as a completed tournament.
- `min_elapsed_sec` produces a HOST-FACING BADGE, never a rejection — Arcaid sees submit time, not play time. Don't let anything turn it into enforcement.
- `applyLibraryDefaults` (`src/utils/gameLibraryDefaults.ts`) is shared by `TournamentEngine.activateGame` and the event round start; a creator that skips it renders an unstyled card.

## Throwdowns — room-less events (v2.136.0, ADR 0018)

A **Throwdown** is a player-created challenge with no game room: a `format='event'` tournament with `game_room_id IS NULL`, `checkin_required = 0` and ONE round, addressed by `tournaments.throwdown_code` at `/throwdown/:code`. It is the SAME object as a hosted Tournament Event, so the round clock, the boards, the standings, the frozen result and the public page are all reused — there is no parallel implementation, and adding one would be the mistake this design exists to avoid.

- **`score_history.game_room_id` is NULLABLE as of migration 164** — that one column was the entire cost of going room-less (`tournaments`/`games`/`submissions` already tolerated a null room). **Any new query that groups or filters by room must decide what a NULL room means** rather than assume every score has one. `ScoreHistoryService.log` takes `gameRoomId: string | null` and skips the room-membership write when null.
- **A Throwdown writes `score_history` ONLY** — never `community_scores`, whose room column is still NOT NULL. That is safe because `score_history` is already the physical union every read path uses and `EventResultService` reads by `submitted_during_tournament_id` alone.
- **`checkThrowdownSubmission`** in `EventSubmissionGate` is the room-less sibling of `checkEventSubmission`, keyed on the tournament id instead of `(room, game name)`. Both resolve the window through ONE shared `evaluateWindow` — two copies of "is it open yet" would drift on the buzzer. A room-scoped event is deliberately NOT reachable through the room-less path (it would skip check-in).
- **Deliberately absent:** iScored sync, room name claims, check-in, and notifications (the link IS the notification). **Global-scoreboard fan-out is NO LONGER absent — reversed in v2.153.0 (ADR 0023):** a Throwdown score fans out like any other, through the same `fanOutFromRoomSubmission` (now null-room tolerant, dedup on `origin_game_room_id IS ?`, recorded as `origin_type='global'` since a room-less challenge has no room chip).
- **First-click-wins rematch** is enforced by the UNIQUE index on `rematch_of_tournament_id`, not by the service's pre-flight — that check exists so the second clicker is handed the existing link rather than an error.
- Codes avoid `0`/`O`/`1`/`I`/`l` — read aloud on streams, retyped from phones.
- **Personal rooms were REJECTED** (ADR 0018 records why): they eat the flat public slug namespace, make the share link read as somebody's room URL, and give every room-scoped feature an "except personal rooms" caveat. Do not revive that idea.

## AtGames event score sync (v2.138.0 / v2.139.0, P7)

An event round can source its scores from an **AtGames private tournament** instead of phone re-entry: the cabinet posts to AtGames, `AtGamesEventSyncService` reads AtGames. Separate from `AtGamesApiClient` (public catalogue, no auth) — the authenticated half is `AtGamesPrivateClient`.

- **Auth contract:** `POST /api/arcadenet/api/account/login {email,password}` → take `account.token`; if that response carries none, `POST /api/arcadenet/api/account/sign_in` forwarding login's cookies. Every `/api/retro/api/v1/...` call carries `Authorization: Bearer <token>` **and** `fp: <device-uuid>`. The token is a self-contained HS256 JWT (`{id, email, user_name, full_name, exp}`, ~7-day life) so the AtGames account id needs no lookup; a 401 triggers **exactly one** re-login. Sessions are cached per lowercased email, in-process only. **Never log the token, the password, or an unmasked email.**
- **Creds are per-room and room-only** (`ATGAMES_ENABLED`/`_EMAIL`/`_PASSWORD`/`_DEVICE_FP` in `game_room_settings`, password on the `ENCRYPTED_SETTING_KEYS` allowlist). **No env fallback on purpose** — a server-wide account would sign every room in as one person. Partial config = OFF + WARN, same rule as iScored. `ATGAMES_DEVICE_FP` is minted once and persisted; a fresh uuid per boot reads as a new device to AtGames.
- **`score_history.source = 'atgames'` is the fourth value** (migration 167, a `score_history` rebuild). None of the three existing values fit: `'tournament'` claims Arcaid saw the submit, `'sync'` means iScored and forces unknown provenance (ADR 0016 P2) while these rows know their cabinet, `'community'` means outside a tournament window. Reusing one would make "which of these did we witness?" unanswerable forever.
- **The window is server-enforced against AtGames' timestamp**, through the SAME `eventEndGraceSec` helper the gate and `EventScheduler` use. `parseAtGamesTimestamp` exists because AtGames sends `"2026-08-23 20:54:42.0"` with **no zone** — `Date.parse` would read that as local time and shift every score by the server's offset.
- **Rounds match on (catalogue game, window)**, joined via `global_games.atgames_id` — the payoff for the importer chasing AtGames' stable game id. Same table in two rounds resolves by timestamp; an unmatched AtGames game is counted and named, never guessed at.
- **Identity is a link, never a name match.** `atgames:<account id>` → `user_identity_links`. Unlinked scores still land (complete board) with `submitted_by_user_id = NULL` and the synthetic id in `discord_user_id` — `normalizeSubmitterUserId` rejects `atgames:*` alongside `iscored:*` for the v2.125.2 reason. Ingest is idempotent (the `ScoreHistoryService.log` dedup), so a host may press sync repeatedly.
- **Deliberately absent:** automatic polling on the round clock, admin UI, and any AtGames-side write (no tournament creation). **Global Scoreboard fan-out is NO LONGER absent — reversed in v2.153.0 (ADR 0023)**, but only for a LINKED account: an unlinked `atgames:<id>` credits nobody, so it stays on the room board alone. `'atgames'` is also NOT whitelisted in the per-row score-delete endpoint — with no tombstone table the next sync would resurrect the row (the iScored equivalent is `deleted_score_suppressions`).
- **Exit-to-submit means `created_at` is when the player LEFT the table.** This proves a score landed inside the window and nothing else; play duration stays unknowable until P8's on-device witness. Never describe it as more. **AtGames does NOT filter gear-up** (owner-tested on hardware 2026-08-25: a game started before the window and exited inside it is accepted onto their board), so nothing upstream helps either.
- **v2.139.0 added the host controls:** credentials on the room Settings page (`ATGAMES_ENABLED` toggle + the two cred fields; `ATGAMES_DEVICE_FP` is claimed by `managedKeys` so it never renders as an editable input), and an AtGames section in `EventRoundsPanel` — id field, **Preview**, **Pull scores**, a per-score verdict list, and the "Who is who" account linker. **The dry run and the real write share ONE dedup predicate** (`ScoreHistoryService.isDuplicate`, extracted from `log`) — never re-implement it, or the preview will disagree with the run it previews.
- **v2.140.0 first-live-test fixes:** `tournaments.discord_channel_id = 'none'` is the per-tournament "don't announce" sentinel, honoured ONLY inside `resolveAnnouncementChannelId` (`ANNOUNCE_NONE` in `src/utils/discord.ts`) — `EventScheduler.announce` now routes through that resolver too (its old local fallback chain is what let a test event post into a live channel); never compare against `'none'` anywhere else. `AtGamesEventSyncService.resolveAtGamesId` accepts an INVITATION CODE (or name) where the numeric id belongs, resolves it via `listPrivateTournaments`, and writes the numeric id back. `createForTournament` creates the AtGames tournament FROM the event (window = first round start → last round end + `eventEndGraceSec`; gameIds via the same `mapRoundsToAtGamesIds`; refuses when already linked; names unresolvable games in the error). `EventService.createOrUpdateEvent` REOPENS a finished event when the save includes a round whose window is still ahead (clears `event_finished_at`/`event_result`, sets `is_active = 1`) — finishing recomputes the result from `score_history`, so clearing it loses nothing. `EventSettingsFields`' round/check-in times use the local `DateTimeField` (date input + hour/minute selects), not `datetime-local` — Chrome's native time wheel skips values when scrolled; off-step stored minutes render as themselves, never snapped. **v2.140.1:** `AtGamesApiError` carries AtGames' response body up to the admin (`ATGAMES_REJECTED`, 502) — the create payload contract is reverse-engineered and live AtGames 400'd the first attempt, so their body text is the diagnostic; never let a non-401 axios error escape `AtGamesPrivateClient` raw. The Who-is-who link authorization and picker are **members ∪ this event's participants** (a fresh test room has NO members; the hand-added admin is a participant). The live create contract is STILL unsettled — an owner capture of a manual create POST (Copy as cURL) settles it.
- **v2.141.0:** the AtGames CREATE contract is **CONFIRMED** (owner cURL: `{name,startDate,endDate,gameIds}` ISO UTC; AtGames 400s a PAST startDate — `createForTournament` clamps start to now+60s and refuses an already-over event). **Players self-link at Account Settings → "AtGames cabinet account"** (`POST/DELETE /api/auth/link/atgames`): ownership proven by ONE in-flight AtGames sign-in, only the `atgames:<id>` row is kept — NEVER store the password; both self-link and admin "Who is who" funnel into `AtGamesIdentityService.linkAccount`, so guard/claim behaviour cannot fork. The Account Settings Google list filters `atgames:*` rows OUT (their unlink must re-anonymise via the dedicated endpoint, not the generic row delete). **Event discovery**: `EventBanner` renders from `PublicLayout` (beside `NotificationNudgeBanner`, suppressed on `/events/` paths) off the public tournaments list — do not add per-page copies. Event + Throwdown login offers BOTH IdPs. **Participant add accepts `@username`**: `@` demands resolution, a bare string resolves only on exactly-one match and otherwise passes through as a raw id (the pre-v2.141 contract — test fixtures and `google:*` ids arrive that way); ambiguity is a 409, never a guess.
- **Arcaid Witness (v2.142.0 ingest + v2.145.0 verify-join, ADR 0020).** An app on the cabinet reports table `launch_ts`/`exit_ts` (epoch SECONDS, device clock) into `witness_observations` over a synchronous **GET** — the AtGames SDK offers no POST — authenticated by a device-scoped token bound to `ATGAMES_UNIQUE_ID`, minted via a single-use pairing code and **stored only as a SHA-256** (`witness_devices.token_hash`; a wrong token gets a bare 401). `WitnessVerifyService.verdictsForRound` joins each `source='atgames'` board row to an observation on **`exit_ts ≈ created_at` (±`JOIN_TOLERANCE_SEC` = 120)** — exit-to-submit makes those the same instant on two clocks, so the join doubles as a device-clock check (drift ⇒ no match ⇒ `unwitnessed`, never a false pass); `launch_ts >= roundStart − LAUNCH_GRACE_SEC` (15) ⇒ `verified`, earlier ⇒ `flagged` (the gear-up P8 exists to catch). **Badge, never a gate** — no verdict filters a board or changes a rank, and `unwitnessed` is NEUTRAL (most players have no paired cabinet). `table_name` is the engine-internal id and is surfaced but **never matched** against the catalogue (different namespaces, no mapping). **`created_at` on atgames rows now holds ATGAMES' timestamp**, threaded through `ScoreHistoryService.log`'s optional `createdAt` (SQLite UTC shape) — any new ingest path that stamps somebody else's timestamp must pass it, or its scores can never be witness-verified; `isDuplicate` still ignores the column so re-pulls dedup against pre-v2.145.0 rows.
- **Witness verification is THREE TIERS as of v2.148.0 (ADR 0021).** Tier 1 = the session join above (`method:'session'`). **Tier 2 = a round-start CHECK-IN** (`GET /api/witness/checkin`, same device-token auth and same bare 401 as `/witness/report`): these cabinets run one thing at a time, so the Witness being open at `server_ts` proves no table was mid-session then — a score that exited after a check-in inside `[roundStart − LAUNCH_GRACE_SEC, score.created_at]` is `verified` with `method:'checkin'` and NO duration. **`witness_checkins.server_ts` is the SERVER's clock, always** — a device-supplied time would make tier 2 a self-report worth nothing; tier 2 only ever UPGRADES an `unwitnessed` and can never produce `flagged`, and never revisits a tier-1 verdict. Tier 3 = retro-derived observations (`witness_observations.via = 'retro'`, `?via=retro` on the report route, first-writer-wins in the upsert): **same trust, tagged** — never gate on `via`. A check-in proves the CABINET was idle and cannot bind a score to a device (AtGames exposes only a model code, `AtGamesRanking.hardware`) — accepted, documented, still a badge and never a gate. **Late evidence is re-frozen by `POST /:roomId/admin/tournaments/:tournamentId/reverify`** → `EventResultService.recomputeFrozenResult`, which reuses `computeStandings` + `freeze` and touches NOTHING else: `event_finished_at` and `is_active` are preserved and **nothing is announced** (a second podium post hours later reads as a second event). Throwdowns have no admin surface, so no reverify.
- **VPXS AUTO SCORE COLLECTION (P9, ADR 0022).** VPX on an ALP cabinet runs under the third-party **vpx-standalone** launcher, so AtGames never sees these tables and there is NO leaderboard to sync — the Witness reads the launcher's own `scoreserver/vpx-<table>-games.jsonl` off the same stick it runs from and reports each completed game to `GET /api/witness/score` (device-token auth, same bare 401 as report/checkin), landing via `VpxScoreIngestService`. `score_history.source = 'vpx'` is the **fifth** value (migration 172, a second `score_history` rebuild — on the SHARED `rebuildScoreHistorySource` helper that migration 167 now also calls; never hand-copy that create-copy-drop-rename again). **The ingest writes the GAME as a `witness_observations` row** (`launch_ts` = game start, `exit_ts` = game end): a VPX sitting holds several games, so verifying against the SESSION's launch would flag every legitimate second and third game — filing the game means the ADR 0020 join needs no VPX rule, only source eligibility in `WitnessVerifyService`. Matching mirrors AtGames exactly (the game's END time decides the round; an early start is `flagged`, never refused at ingest — badge, never gate) and is scoped to the player's rooms' ACTIVE rotation games + rounds of events they are in; **pinned boards are deliberately NOT candidates** (no window = unbounded writes from ordinary play at home). Names match on any of journal-name/`rom`/slug through `normalizeGameName` plus a squashed form (`vpx-badcats` → `badcats`) because `rom` is heterogeneous and sometimes wrong; **two matches is `no_match`, never a guess**, and an event round beats a rotation game of the same name. Player 1 only (the launcher stamps the cabinet's own account on every row), games < 20s dropped, and the launcher's continuation artifact (a short record starting the instant the last one ended, repeating its total) dropped. An unmatched score answers `200 {status:'no_match'}` — NOT a 401 — so the cabinet never retry-loops on ordinary play.
- **WITNESS SCORE ROUTING (P9b, v2.152.0).** Each PAIRED CABINET carries its own designation (`witness_devices.target_room_id` / `target_tournament_id` / `global_fallback`, migration 173; set at Account Settings -> paired cabinets via `PATCH /api/me/witness/devices/:deviceId`, validated: the room must be one the player is a member of and the tournament must be in that room). **It NARROWS the candidate set, it does not route past the matching** - name and window still decide, and two survivors is still never a guess. **The model:** designated -> that room (further narrowed by the tournament, which is the ONLY thing that can resolve the same table open in two tournaments of one room) · undesignated -> EVENT ROUNDS of events the player is a PARTICIPANT of ONLY (joining an event is the deliberate, time-boxed act a designation would otherwise supply; **a rotation tournament REQUIRES the designation**, because it runs for days with no per-session act and ordinary play at home must not quietly enter somebody into a competition) · anything left over -> **the GLOBAL SCOREBOARD** (`originType: 'global'`, engine `vpx` / device `atgames`, deduped on (player, catalogue game, score)), so a cabinet that is paired and then forgotten still earns the player a personal record. That last step is why ADR 0016 P2's bar on `'sync'` reaching Global is NOT violated: it bars scores whose provenance is unknowable, and a witness score's is exact. **`global_scores.global_game_id` is NOT NULL, so a table missing from the catalogue simply cannot be recorded globally** - reported as `no_match` with a reason, never invented; same-named machines are told apart using the manufacturer/year parenthetical in the launcher's own display name. A designated tournament that has FINISHED reads as ABSENT (read-time expiry, no cleanup job), and `loadCandidates` ignores games of inactive tournaments entirely. The check-in response carries `sendingTo` so the cabinet prints where its scores are going - the defence against a stale designation is that the player sees it before the round, not after.
- **`AtGamesIdentityService` owns the link.** `atgames:<id>` → `user_identity_links` (no new table — an AtGames account is a provider identity nobody logs in with). `linkAccount` claims already-ingested rows behind the SAME freeze gate `MergeService.previewMerge` uses (skip rows in an `is_active = 0` tournament), refuses a re-point with `LINK_CONFLICT` rather than last-write-wins, is idempotent for the same target, and invalidates identity caches only when rows actually moved. `unlinkAccount` re-anonymises `source='atgames'` rows ONLY. The room-admin route bounds a global write by requiring the target to be a member of that room — same asymmetry as iScored claim approval.

## Platform stratification

`platform` is required at the API boundary on `submissions`/`score_history`/`community_scores`/`global_scores` (column nullable in SQL for legacy rows).

**Tournament rules are two-AXIS as of v2.60.0 (ADR 0016 P2):** `{ engines: {required, excluded}, devices: {required, excluded}, restrictedText? }`, axes evaluated independently and AND-combined. Within each axis, ADR 0009's orthogonal semantics are unchanged:

- **`required` ("Must be available on") → game-level eligibility ONLY.** `passesplatformRules(gamePlatforms, rules)` checks the game has at least one platform denoting a required engine AND one denoting a required device; decides which games qualify. Does NOT restrict which platforms can submit scores.
- **`excluded` ("Not allowed on") → submission-level filter ONLY.** `resolveSubmittablePlatforms(gamePlatforms, tournamentRules?)` strips platforms excluded by EITHER axis (required is intentionally not applied here). Does NOT restrict game eligibility.

**Every runtime read of `tournaments.platform_rules` goes through `parseTournamentRules` (`src/utils/platformRules.ts`)** — 10 routed sites, malformed JSON logs a WARN naming the tournament then degrades to empty rules; never hand-roll a `JSON.parse` of this column (the 3 migration parses — 101/083/089 — are deliberately raw frozen transforms). The parser is also the read-time shim: ~200 rooms still store the flat legacy shape (`{required, excluded}` over legacy platform ids), lifted at read via `LEGACY_PLATFORM_MAP` (both-axis ids like `vpxs` → engine `vpx` + device `atgames` restrict BOTH; unknown room-invented tags kept verbatim on the engine axis). Writes always emit the two-axis shape (Zod preprocess + `TournamentService.create/update` both normalize); stored rows upgrade only when an admin re-saves.

Example: WHO dunnit on `[vpx, vpxs, real, fx, fx_vr, atgames]`. Legacy rule Must=`[atgames]` lifts to `devices.required=[atgames]`. Game qualifies (has atgames). Picker shows all 6 platforms — player may submit a vpx, vpxs, real, fx, fx_vr, or atgames score.

`SubmissionSheet` reads via `GET /api/submit/platforms` which returns `{ platforms, submittable, tournamentRules }`. One platform → read-only chip; 2+ → required dropdown. Chip caption disambiguates with `fullGamePlatforms.length > 1` → "(only platform allowed by this tournament)" else "(only platform for this game)". Discord `/submit-score` auto-fills when 1, prompts when 2+. Server re-validates at every submit handler (`ensurePlatformAllowed`, also strict-excluded-only). `/leaderboard/:gameId?platform=X` returns `distinctPlatforms[]` for the GameDetail tab strip. See ADR 0006.

**Provenance is remembered, per-game before global (v2.149.0).** `arcaid_last_provenance:<gameKey>` (JSON `{engine, device}`, checked FIRST) → `arcaid_last_engine` / `arcaid_last_device` (the global "my rig" keys; the device one dates to v2.53.0) → auto-lock when only one option fits → empty. Room targets key on `(roomId, lowercased game name)`, NOT a game id — a tournament game row is recreated on every rotation, so an id-keyed memory would forget exactly when the table comes round again. **Every remembered value must be tested against the same exclusion-filtered option list the dropdown renders** (`allowedEngines` / `allowedDevicesForEngine`); the v2.95.1 field bug was a membership test against the unfiltered list, which submitted `pc` while the `<select>` displayed "AtGames Cabinet".

**Score ENTRY is comma-grouped (v2.149.0).** `admin-ui/src/lib/scoreInput.ts` — the sheet's `score` state holds the FORMATTED string so `lib/caretEdit`'s splice helpers and the browser's `selectionStart` index the same thing the player sees; every numeric read goes through `digitsOnly` first. Grouping is done by string, not `toLocaleString`, so it stays exact past `MAX_SAFE_INTEGER` and cannot pick up a locale whose separator disagrees with `formatScore`. Caret positions are carried across a re-group as a DIGIT COUNT (`reformatScoreEdit`), because inserting a digit into `999,999` also shifts every separator. The field is `type="text"` on desktop too — `type="number"` refuses a value containing separators and is the one input type whose `selectionStart` throws. `formatMagnitude` prints the plain-language echo ("6.66 billion", truncated never rounded) that is the actual defence against an extra digit.

**When adding/changing a platform:** update `src/utils/platformMapping.ts` AND mirror to `admin-ui/src/lib/platforms.ts` (FE has its own copy of `CANONICAL_PLATFORMS` + `PLATFORM_ALIASES`). Forgetting causes silent FE/BE drift.

## At-rest secret encryption

`src/utils/secrets.ts` provides AES-GCM keyed off `SECRETS_KEY` env (mint via `npm run generate-secrets-key`). `ENCRYPTED_SETTING_KEYS` is a deliberate allowlist (no convention-based auto-encrypt). **Adding a new secret means adding it to the allowlist** — typo-proofing. `SettingsService` and `GameRoomSettingsService` consult `isEncryptedKey(key)` for encrypt-on-write / decrypt-on-read. `maskEncryptedValues` returns `[ENCRYPTED]` placeholder on `GET /admin/settings` so the UI never round-trips ciphertext. See ADR 0003.

## Lobby, social, notifications

- **Lobby feed** lives in `lobby_feed_events` (separate from `room_events` — 90-day retention vs 7, different query patterns). Cursor pagination via `created_at`. WebSocket channel `lobby:${roomId}`. `LobbyFeedGenerator.onScoreSubmitted` is hooked into all score submission paths via fire-and-forget dynamic imports. Lobby config (social links, pinned message, feed settings) stored as JSON in `game_room_settings` keys — no new tables.
- **Friends** use a unidirectional follow model. `FriendsService.getPlayersWhoFriended` is the reverse lookup driving targeted `friend_score` events.
- **`NotificationService.notify`** checks per-user opt-in prefs (`notification_prefs` JSON on `user_preferences`) + in-memory rate limit (5/user/hour). - **Milestones** use "exactly equals threshold" count queries — no separate tracking table.

## Patterns worth knowing

- **Game queue:** explicit `queue_order` column, per player per tournament, **newest-first as of v2.143.0** (owner ruling 2026-08-27: `queueGame` inserts at position 1 and shifts the player's other rows down — every queue path routes through it, so web/Discord/admin-on-behalf agree; pre-v2.143.0 it was FIFO append). Capped at `PICK_QUEUE_MAX` (`src/services/PickQueueService.ts`, 30 as of v2.126.0 — import it, never hardcode the number; the FE gets it as `queueMax` on `/pick-status` and the admin on-behalf queue responses).
- **Queue hold model (v2.126.0):** a queued pick that is inside its cooldown when the engine reaches it is **stamped `games.queue_held_at`, never deleted** (both walkers — `TournamentEngine.nextEligibleQueuedFor` and the extra-slot fill loop in `runMaintenanceWork`). `src/utils/queueOrder.ts`'s `queueOrderSql(alias?)` / `QUEUE_ORDER_SQL` is the ONE ordering fragment — held rows first (oldest hold wins), then `queue_order ASC` (NULLs first, which is how `[Pending Pick]` placeholders keep their front position), then `rowid` — so a held pick activates the instant its cooldown clears, and **every reader must import it** (`/pick-status`, `getPlayerQueue`, `/view-queue`, the admin on-behalf queue, `PickAlertService`, both walkers). A hand-copied `ORDER BY queue_order ASC, rowid ASC` is now a bug: the page would show one order and the engine consume another. `queue_held_at` is cleared on promotion alongside `queue_order`; `PUT /queue/reorder` renumbers UNHELD rows only. Every removal/promotion calls `PickQueueService.compactQueue(tournamentId, pickerId)` so stored positions stay a gapless 1..N, and the three ENGINE consumption sites additionally fire `QueueLowNudgeService.maybeNudge` (the opt-in `queueLow` notification, deduped in `queue_low_nudges`) — a player's own delete deliberately does not.
- **Tournament rotation guards:** `processSlotMaintenance()` checks `max_active_games` and existing `[Pending Pick]` rows before creating picker slots. `TimeoutManager.fallbackToAutoSelection()` includes orphan cleanup.
- **Per-slot picker dedup (v2.9.0):** picker placeholder dedup is keyed `(tournament_id, picker_discord_id, won_game_id)` — was `(tournament_id, picker_discord_id)` pre-v2.9 which collapsed multi-slot wins (e.g. WG-VPXS max=2 with the same player on top of both got one prompt + one DM, only one slot got refilled). DM and channel embed both name the won game. `won_game_id` is not an FK with cascade — admin removing a completed game leaves the placeholder dangling, but `GET /:roomId/pick-status` LEFT JOINs so `won_game_name` falls null gracefully and the FE clause is conditional.
- **Discord `/pick-game` placeholder fulfillment (v2.9.0):** the Discord command now mirrors the web `/pick-game` route's three-branch flow — pending+full repurposes the placeholder (keeps `queue_order = NULL` so it stays at the front of the queue), open-slot drops any existing placeholder inside the activate transaction, no-pending+full queues normally. Pre-v2.9 the Discord command branched only on `hasOpenSlot` and left placeholders dangling.
- **Cleanup-race fix (v2.9.0):** Wed `0 22 * * *` daily maintenance + `0 22 * * 3` scheduled cleanup fire at the same instant; pre-fix the cleanup query ran before maintenance had completed today's active game and missed it. Now `runMaintenanceWork` runs cleanup inline at the end of the slot loop when `cleanupRule.mode === 'scheduled'` AND the cleanup cron's `min/hour/dom/mon/dow` would all match right now in its timezone (`cleanupCronMatchesNow` helper). Separate cleanup cron stays registered — fires idempotently.
- **Ranking-group cache watermark (v2.10.1):** `ranking_groups_cache` self-invalidates via a fingerprint over indexed columns — `(eligible_games_count, score_count, score_sum, MAX(end_date), MAX(start_date))` for the group's tournaments. `RankingService.getRankings` recomputes the watermark on every read; mismatch with the stored snapshot triggers silent recompute. **No mutation code path needs to call `RankingService.invalidate*()`** for score / game-status changes — the data tells us when it's stale. Manual "Recompute" admin button retained as a diagnostic escape hatch but is no longer load-bearing. `RankingService.update()` (config changes, not data changes) is the one path that still calls `invalidate()` directly. Sub-10ms watermark vs. ~50-200ms recompute — net win on every cache hit. See ADR 0013.
- **Manual card order is a self-invalidating override (v2.118.0):** room scoreboard order = `COALESCE(g.display_order, t.display_order, 9999), g.start_date` (`LeaderboardService.getActiveLeaderboards`; `games.display_order` has NO writer — leave it that way). An admin drag on the admin Leaderboard page stores `game_room_settings.LEADERBOARD_CARD_ORDER` (NOT a `SCOREBOARD_*` key — that prefix is auto-public via `/scoreboard-config`) with a fingerprint of each tournament's `display_order` + sorted ACTIVE game ids; `CardOrderService.applyCardOrderOverride` (pure) applies it at READ time: any fingerprinted tournament's `display_order` changed → whole override ignored; a tournament's ACTIVE set changed → only its ids drop (rotation by any path — no hooks in TournamentEngine/TimeoutManager, don't add any); slot-fill merge for the rest. **Save and read MUST compute the fingerprint through the same `loadCurrentState`** or the override self-destructs on the next read. Arrows (`HorizontalScrollNav`, fixed z-40 portalled to body) are off on the admin page (`hscrollArrows={false}`) — they cover the rail column by construction.
- **Room-admin observability (v2.15.0, S10):** `GET /:roomId/admin/health` aggregates four things → (1) Discord gateway readiness + guild membership via `getDiscordClient()?.isReady()` / `.isInGuild(guildId)`. **The live `DiscordClient` is reachable via the module-level `getDiscordClient()` accessor** (set in its constructor); pre-S10 the gateway `Client` was a private field on a throwaway local in `index.ts`, so every "bot online" check (`DashboardService`, `/api/status`) was env-var *presence*, not connection state. (2) `ScoreSyncPoller.getStatus()` — global + per-account (`accountHealth` map) last-success / last-error timestamps + consecutive-failure counts. (3) Per-tournament last run from **`maintenance_runs` (migration 106)** — `runMaintenance()` records one row (`success` / `skipped` / `error` + summary + duration) for every cron *and* forced run via `MaintenanceRunService`; append-only, **no FK** (an audit log that outlives its tournament, like `games.tournament_id`). (4) `getVersionInfo()`. Force Maintenance (`POST .../game-states/force-maintenance`) now **awaits** the run and returns the real outcome (was fire-and-forget + a blind 3s FE refetch). **`OpsAlertService.sendOperatorAlert`** DMs a super-admin after `OPS_ALERT_FAIL_THRESHOLD` (5) consecutive poller failures for one account, debounced once-per-outage + re-armed on recovery — **ships inert** behind global settings `OPS_ALERT_ENABLED` + `OPS_ALERT_DISCORD_USER_ID` (both unseeded → off; not encrypted — a user ID isn't a secret). App version: `GET /api/version` → `{version, commit, builtAt}` (version from root `package.json` via `npm_package_version`; `commit`/`builtAt` from `APP_GIT_SHA`/`APP_BUILT_AT` env baked by `deploy.yml` `GIT_SHA`/`BUILT_AT` build-args in the `Dockerfile` prod stage) — **NOT** the SW `CACHE_NAME`.
- **OG link-preview meta (v2.24.0, S16):** the SPA catch-all in `server.ts` serves `index.html` with `og:*`/`twitter:*` tags injected (via `src/api/ogMeta.ts`) ONLY when the UA matches the curated preview-bot list AND the path is `/:slug/games/:name` or `/:slug/players/:id`. Humans always get the unmodified shell; every failure falls through to it; `OG_META_ENABLED=false` global setting is the kill-switch (default on); bot requests pass through `ogPreviewLimiter` (60/min/IP — the catch-all is outside the `/api` generalLimiter). FE sharing via `components/ShareButton.tsx` (`navigator.share` → clipboard → execCommand fallback chain).
- **Style catalogue is global** (shared across rooms). Per-game overlay via `logo_style_id` + `bg_style_id` on `games` and `game_room_game_library`. Resolution: `effectiveBgId = bgStyleId || catalogueStyleId`.
- **Image upload limit** 30MB. Formats PNG/APNG/JPEG/WebP. APNG animates natively in `<img>` tags.
- **Score abbreviation:** scores ≥1T render as `X.XT` with full value in tooltip.
- **Score toast:** WebSocket `score:new` carries `{ gameId, gameName, playerName, score }`; Scoreboard shows slide-down toast.
- **Live pages must also recover when the socket does NOT deliver (v2.154.0).** `hooks/useLiveRefresh.ts` refetches on RE-connect (room membership is per-connection, and pre-v2.154 every page re-joined `room:<id>` on `connect` but reloaded nothing — so scores submitted during the gap were never seen), on visibility / `pageshow` / window `focus`, and on a 60s poll that is skipped while `document.hidden`. One 5s throttle across all three. `pageshow` is required because iOS bfcache fires neither a visibility change nor a socket event; `focus` because a desktop alt-tab fires no visibility change. **Any new page that calls `socket.emit('join:room', ...)` needs this hook too** — the four are Scoreboard, KioskScoreboard, GameDetail and the admin Leaderboard. The hook owns only the recovery; each page keeps its own event handlers and decides what to reload.
- **Themes:** 16 themes in CSS variables (15 `.theme-*` classes + the no-class dark default) — the ONE list is `THEME_IDS` in `admin-ui/src/lib/themeIds.ts`, which `THEMES` (picker), `ALL_THEME_CLASSES` (class stripper) and the API's Zod enum are all derived from; **dropped ids map through `LEGACY_THEME_MAP` in that same module (FE `lib/themeIds.ts` ≡ BE `utils/themeIds.ts`, parity-locked by `themeIds-parity.test.ts`), applied by `normalizeThemeId` at every READ of a stored id (localStorage mirrors are not migratable) and by migration 162 on the three stored sites; every theme label/description must describe the rendered palette** (background tone, ink, accents — not a metaphor), ≤ 60 chars, checked against its `.theme-<id>` block. **One resolution order as of v2.132.0** (documented in a block at the top of `ThemeProvider.tsx`): room public pages take this-room override (`scoreboard_prefs.roomThemes[roomId]`) → personal theme (`user_preferences.ui_theme`, NULL = use each room's default) → room default (`game_room_settings.UI_THEME`) → `dark`; admin pages take personal theme → `dark`; global pages are polarity-only — so the personal theme is ONE picker (Display settings / Account settings / Global Settings, all via `components/ThemePicker.tsx`) and the room-settings "Admin Theme" field is gone. **The this-room override is keyed by ROOM, not by device**: it rides in the `scoreboard_prefs` JSON as a third top-level key beside `desktop`/`mobile` (`PreferencesService.getRoomThemes`/`setRoomTheme`, `GET`/`PUT /api/me/room-themes`), because the pre-v2.132 `scoreboard_prefs[device].UI_THEME` was one control labelled "this room" that actually applied to every room on one device; `getRoomThemes(userId, roomId)` performs the one-shot idempotent lift of that legacy key onto the room being viewed. `ThemeProvider` reads localStorage first to avoid flash (`arcaid-theme-personal`, `arcaid-theme-room-<slug>`, `arcaid-theme-public-<slug>` — the last two are deliberately separate keys: `setPublicTheme` writes the room DEFAULT into the `public` one from the admin Settings page). **The viewer's Appearance preference (`dark`/`light`/`auto`, v2.130.0 — `localStorage['arcaid-appearance']` + `user_preferences.appearance`) is the LAST step of resolution on every route class**: `resolveAppearance(base, appearance)` keeps a theme whose `THEME_POLARITY` (the map beside `ALL_THEME_CLASSES`, derived from `color-scheme` in `index.css`; only `light`, `arctic`, `paper` + `speegle` are light) already matches and otherwise swaps in the canonical `light`/`dark` theme — so classify any new theme there or it silently never matches. **A card whose artwork FILLS it is a dark-token island** (v2.131.1): its root carries `sb-theme-scope sb-on-art` so the text over the fixed black scrim is theme-independent (`sb-on-art` re-anchors the inherited `color` and shadows every `sb-art-text` element) — any NEW card style that paints artwork under a scrim must do the same, or its text goes near-black-on-black under a light theme. **Contrast bar (v2.131.2): in EVERY theme `--color-muted` must clear 4.5:1 against `--color-deep`/`--color-surface`/`--color-raised` and `--color-faint` must clear 4.5:1 against `--color-deep`/`--color-surface`** (faint carries real content — "Never", timestamps, captions — not decoration); re-run `node admin-ui/scripts/contrastAudit.cjs` after adding a theme or retuning a token.
- **PWA:** `manifest.json` + `sw.js` in `admin-ui/public/`; service worker is cache-first for static assets, network-first for navigation.
- **Public slug matching is case-insensitive.**

## Gotchas (silent-failure mode)

- **Service-worker cache-bust is automatic (v2.28.0+), no manual bump ever.** `admin-ui/public/sw.js`'s static cache name (`arcaid-static-${BUILD_ID}`) is derived at build time by the `arcaid-sw-build-id` Vite plugin (`admin-ui/vite.config.ts` + `admin-ui/scripts/swBuildId.ts`) — a sha-256 over the emitted asset filenames + `index.html`, truncated to 12 hex chars, injected in place of the `__ARCAID_BUILD_ID__` placeholder during `closeBundle`. Same source → same BUILD_ID (deterministic); the build throws loudly if the placeholder or `dist/sw.js`/`dist/index.html` are missing. Activate deletes every cache except the current `STATIC_CACHE` and the stable `IMAGE_CACHE` name, so old `arcaid-static-*` generations (and legacy `arcaid-v###` caches from pre-v2.28 installs) are swept on the next install. Image mounts (`/api/catalogue-images`, `/api/styles/images`, `/api/room-assets`, `/api/score-photos`) are routed separately into `IMAGE_CACHE` — stale-while-revalidate, LRU-capped at 200 entries — so they no longer grow the static cache unbounded. `sw.js` and `index.html` are served with `Cache-Control: no-cache` (`src/api/server.ts`'s `frontendStaticOptions` + the SPA catch-all) so an installed PWA always revalidates and picks up the new BUILD_ID; `/assets/*` (Vite's content-hashed bundle output) is `public, max-age=31536000, immutable`. `vite dev` serves `public/sw.js` raw with the placeholder intact — harmless, dev never goes through the build plugin.
- **Never swap an `admin-ui/public/` asset in place — new filename every time.** Same-name overwrites go stale for days: pre-v2.45.1 those files shipped with NO Cache-Control, so browsers applied heuristic freshness (a file unchanged for months serves stale without revalidating), and the PWA/OS icon cache compounds it (user saw the old app icon even after delete+reinstall). v2.45.1 added explicit headers (`manifest.json` no-cache; other public statics `max-age=86400`) which only bounds the damage to a day — renaming (`-v2` style, plus `manifest.json?v=N` link when icons change) is the actual fix. Hashed `/assets/*` bundle output is immune (immutable by content hash).
- **"Arcaid Chat Responses" (internally still `callouts`, v2.123.0 → v2.125.0).** `callouts` table (migrations 155/156: `category` ∈ `help|callouts|banter|easter_eggs`) edited via Admin → Settings → Arcaid Chat Responses (upload/replace/export JSON, inline editor, category filter); `CalloutService` caches in memory; the `callouts` table is the ONLY source of truth — the legacy `data/callouts.json` seed file was deleted from the repo 2026-08-23 (prod's list was uploaded via the admin page on 2026-08-21 and is newer/larger than the file ever was; `seedFromFileIfEmpty` still no-ops when the file is absent, so a fresh install starts with just the auto-seeded `help` rows); `ensureBuiltinHelpEntries()` seeds one `help` row per live `action` that has no row. Per-room keys `CHAT_RESPONSES_ENABLED` (absent = off), `_CATEGORIES` (JSON array, absent → `["help","callouts"]`), `_CHANNEL_IDS` (JSON array, empty = any readable channel), `_COOLDOWN_SEC` (default 30; `help` never throttled); the room card saves these INSTANTLY (changed keys only, rollback on failure) — NOT via the Save bar (a staged-only toggle let the bot keep replying after the owner "turned it off"). Legacy `CALLOUTS_ENABLED`/`CALLOUTS_CHANNEL_ID` are migrated at boot then deleted. Gate order in `src/discord/callouts.ts`: DM → legacy `ENABLE_CALLOUTS='false'` → guild scope → room master → allowed channels → in-chat "Arcaid, shush/unmute" → per-user mute (`notification_prefs.chatResponses`) → filter to enabled categories BEFORE matching → match → per-channel cooldown → reply. Live `action`s: `active_games`, `picks_link`, `scores_link`, `how_to_submit`, `time_left` (cron-parser, tournament tz), `leaders`, `my_rank`, `pick_status`, `tournament_rules`, `how_to_claim`; static responses may use `{room_name}`/`{room_url}`/`{picks_url}`/`{scores_url}`.
- **The local `arcaid-bot` container IS a second production bot** if it runs — the repo `.env` holds the prod `DISCORD_BOT_TOKEN`. On 2026-08-21 it had been running ~13h after a reboot: it re-registered the GLOBAL slash-command set from its stale build on every boot, raced prod on every interaction (`DiscordAPIError[40060]`), and answered callouts from the local file. Its restart policy is now `no`; never leave it up alongside prod, and prefer a separate dev bot application for local work.
- **Tailwind on Windows:** must use `@tailwindcss/postcss` (NOT `@tailwindcss/vite` — oxide scanner fails silently).
- **CRLF flips on Windows — both Write AND Edit tools.** A full-file `Write` over a CRLF-tracked file flips every line to LF (known); during S22 (2026-07-26) the `Edit` tool did the same to `src/api/routes/global.ts` — a ~3700-line whitespace-only diff. Detect with `git diff --numstat` vs `git diff -w --numstat` (must be byte-identical); fix with `unix2dos` + verify `git diff -w` shows zero content change. Check this before every commit that touched large backend files.
- **Express v5:** `req.params` values typed `string | string[] | undefined`. Cast `as string` at use site.
- **`rotating-file-stream` types** are at `dist/types/index.d.ts`, not the package root.
- **node-cron** does NOT support `L` (last day of month). `Scheduler.resolveCron()` maps `L` → `28-31` and runtime-guards inside the job.
- **Discord ActionRow** holds max 5 buttons. Star-rating + Skip required splitting into multiple rows.
- **Production container is `arcaid`** (not `arcaid-bot`). No `sqlite3` binary inside — use `node -e` with the existing JS package for ad-hoc DB queries.
- **Legacy alias URL rewriting:** Express strips the mount path, so `/api/leaderboard`-style aliases must explicitly reconstruct the full `/api/rooms/:roomId/...` path including segment.
- **Cross-component DOM events:** PublicLayout (nav) ↔ Scoreboard (Outlet child) communicate via `window.dispatchEvent(new Event('open-scoreboard-prefs'))`. Used because React Router `<Outlet />` doesn't pass props down.
- **Background-sync routes** (`/admin/catalogue/sync-opdb`, `/sync-igdb`) validate credentials upfront and return `400` with an actionable message — pre-fix they returned `202 started` and threw silently.
- **Long-running imports** (IGDB bulk sync, big VPS pulls): never run in foreground, and back up `data/arcaid.db` first if the operation touches schema.
- **Fan-out try/catch swallows column errors silently.** When changing schema in any score table, verify the fan-out path's column references against the live schema.
- **Discord embed colors:** daily=gold(0xFFD700), weekly=blue(0x00BFFF), monthly=purple(0xAA00FF), custom=green(0x00FF88).
- **Playwright base image is hard-coupled to the npm `playwright` version.** The Dockerfile prod stage is `FROM mcr.microsoft.com/playwright:v<X>-noble` with **no `npx playwright install`** — browsers come *only* from the base image, so the npm `playwright` version MUST equal the base-image tag. Bump one without the other and the container's browsers mismatch → every `IScoredClient` op (game create/hide/delete, `/sync-state`, tournament maintenance rotation) throws `Executable doesn't exist` at runtime. **No CI gate catches it:** vitest mocks Playwright and the Docker build never launches a browser. When bumping `playwright` — including any Dependabot backend-minor-patch group that happens to include it — bump the `Dockerfile` base-image tag in the SAME commit/PR (they must land in one deploy; splitting breaks prod in either merge order). Surfaced by the 2026-07-05 safe-wave 1.58.2→1.61.1 bump. **The base moved `jammy`→`noble` in the sqlite3-6 migration** (noble = Ubuntu 24.04, glibc 2.39; sqlite3 6.0.1's prebuild needs `GLIBC_2.38`, which jammy's 2.35 lacks — the app would crash on DB init at boot). Noble also ships Node 24, so the prod runtime is Node 24 (pinned via NodeSource `setup_24.x`). **CRITICAL: `arcaid` is pinned to uid 999 in the Dockerfile** — noble's default `useradd` assigns 997, but the bind-mounted `/app/data` + existing `arcaid.db` are owned by uid 999 (from prod's jammy history) and the CMD's `/app/data` chown is non-recursive; without the pin, the 997 user can't write the 999-owned DB → `SQLITE_READONLY` crash on boot (this took prod down on the first noble deploy attempt, 2026-07-05, reverted; fix = `useradd -u 999`). **A fresh-DB boot test does NOT catch this** (a fresh DB is created by the running user, so ownership always matches) — validate any base-image/UID change against a COPY of the prod DB under real Linux permissions.

## Database

SQLite at `data/arcaid.db` (git-ignored). Schema auto-creates on first run. Migrations are an inline array in `database.ts` (NOT a `migrations/` folder of files), run idempotently on startup in array order, tracked by `name` in `schema_migrations`; complex handlers are extracted to `src/database/migrations/*.ts`. Claim the next free number before coding. Read the migration entries directly for column-by-column intent — that's the source of truth, don't try to maintain a list here.

**Foreign-key enforcement is ON (S3).** `PRAGMA foreign_keys = ON` is set in `initDatabase` **after** the migration loop + `migrateToMultiRoom` (just before `return db`), **never at connection-open** — migrations 066/077/095 are FK-checked table rebuilds (SQLite requires `foreign_keys` OFF for create-copy-drop-rename), and a swallowed 077 `INSERT…SELECT` failure under enforcement would half-migrate a legacy DB. A one-time `PRAGMA foreign_key_check` logs (does not throw) residual violations after enabling. Declared `ON DELETE CASCADE`s are now **load-bearing** (the ~14 `game_rooms` children + ranking/global-game children auto-clean). **New cross-table deletes must either rely on a declared cascade or unlink/clean NO-ACTION children first** — the known NO-ACTION refs are `games.tournament_id`, `submissions`/`scores`/`score_history.game_id` (unlink → NULL, ADR 0005), `global_scores.global_game_id` (NOT NULL → delete) / `origin_game_room_id` (unlink), and `merge_records.anonymous_identity_id`. The fixed delete paths are `TournamentService.delete`, `GameRoomService.delete`, `GlobalGameService.delete`, and the admin "remove game, retain scores" route. **Caveat:** 17 ALTER-added columns (`tournaments.game_room_id`, `ranking_groups.game_room_id`, the `submitted_*` context columns on the score tables, `games.game_room_id`/`won_game_id`) are **pseudo-FKs with no real constraint** — SQLite can't add enforced FKs via `ALTER TABLE` — so integrity coverage is partial, not total.

## Deployment

Production is always Docker (`docker-compose up -d --build`). Admin UI assets build inside the image and are served by Express. Custom domain mapping is infra-level (DNS + reverse proxy). `ngrok http 3001` for ad-hoc public exposure during dev.

After deploy: `docker logs arcaid --tail 50` and verify no restart loop. `JWT_SECRET` must be set or auth breaks on first login.
